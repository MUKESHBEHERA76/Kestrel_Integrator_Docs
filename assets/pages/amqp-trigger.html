Workflow triggers / AMQP

Start a workflow from an AMQP 0-9-1 queue.

AMQP Trigger consumes a message from an existing broker queue, exposes it in the pipeline, runs the workflow, and acknowledges delivery after the workflow succeeds. Create an AMQP project connection first.

Setup

Configure a queue consumer workflow

  1. 1
    Prepare the broker

    Have a broker administrator create the queue, configure any exchange binding, and grant the connection account consume permission. The trigger does not create queues or bindings.

  2. 2
    Create the connection

    Follow Create an AMQP connection, test it, save it, and keep it enabled.

  3. 3
    Add the trigger

    In the workflow editor, drag AMQP Trigger from workflow triggers to the canvas. Connect it to the first processing step. A workflow has one trigger.

  4. 4
    Select the source

    Double-click the trigger. Select the AMQP connection, choose Queue, and enter the exact existing queue name. The field is labeled Existing queue; this runtime consumes by queue name even if a broker exchange is used upstream.

  5. 5
    Set processing and save

    Choose serial or concurrent processing, delivery mode, and prefetch. Resolve workflow warnings, save the workflow, and enable it. Publish a test message to the queue and inspect its execution.

Pipeline contract

Read the received message

The trigger places the received message under ${pipeline.input.AMQP_Response}. In single mode, it is one document. In batch mode, the document contains messages as a DocumentList. The trigger also supplies ${pipeline.input.messageCount} (Integer) and ${pipeline.input.timedOut} (Boolean). A trigger starts a run only after a delivery arrives, so a no-message poll does not start an empty workflow.

PathTypeUse
AMQP_Response.body.messageStringText view of the body. Parse JSON or XML in a following step if needed.
AMQP_Response.body.bytesStringBase64 representation of the body bytes; use for binary payloads.
AMQP_Response.headersDocumentBroker/application headers.
AMQP_Response.propertiesDocumentMessage metadata such as messageId, correlationId, timestamp, priority, redelivered, and destination, when supplied.
AMQP_Response.messages[]DocumentListBatch-mode items, each with body, headers, and properties.

The paths above are under ${pipeline.input.}. No payload schema is enforced by the trigger; validate or transform the body in later steps as needed.

Example

Process orders from RabbitMQ

Create the AMQP connection OrdersRabbitMQ for the broker and virtual host. Ask the broker administrator to create queue orders.incoming, bind the order exchange to it, and give the account consume access. Add AMQP Trigger with Connection OrdersRabbitMQ, Destination type Queue, Existing queue orders.incoming, Processing Serial, and Delivery Single message.

Broker message body: {"orderId":"ORD-1042","total":89.50}
Trigger output:      ${pipeline.input.AMQP_Response.body.message}
Next step:           parse body as JSON, validate orderId, process order

Publish a test message, then review the workflow run. For binary data, read body.bytes and decode the Base64 in a suitable downstream step.

Delivery semantics

Understand success, failure, and scaling

Kestrel keeps the broker delivery unsettled while the admitted workflow runs. It acknowledges only after the run reaches Success. If the run fails or cannot be admitted, the delivery is released or requeued for redelivery. Plan downstream effects to tolerate duplicate processing. An enabled workflow is required for the trigger consumer to run.

Concurrent mode requests several consumer slots, but actual active consumers depend on instance capacity and available broker access. Use a destination that supports competing consumers; tune consumers and prefetch based on measured throughput. The trigger runtime logs connection and receive failures and retries the consumer.
