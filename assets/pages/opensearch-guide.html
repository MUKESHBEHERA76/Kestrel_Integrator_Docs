OpenSearch / Configuration

Register and test the server

An administrator registers one platform-wide OpenSearch endpoint. The browser calls Kestrel; Kestrel sends authenticated requests to OpenSearch. Open the Configuration section, enter the endpoint and authentication fields, select Test connection, then Save configuration after a successful test.

The saved summary shows endpoint, authentication mode, transport security, credential status, and last successful test. Secrets are kept on the server and are not displayed again. A failed test should be resolved before saving; check backend reachability, credentials, TLS trust, and the endpoint scheme.

OpenSearch / Configuration

Manage automated log deletion

Log deletion is a separate configuration card from the server connection. An administrator can edit per-index retention and save the policies. Available periods are 3, 7, 15, 30, 45, 60, and 90 days.

IndexContainsExample retention
kestrel-application-logsApplication/runtime log events15 days
kestrel-project-logsProject-scoped log events30 days
kestrel-springboot-logsSpring Boot service logs7 days
kestrel-execution-logsIndexed execution transactions and step events30 days

OpenSearch deletes expired data during its next index-state-management maintenance cycle. Retention uses elapsed index age, independent of the browser timezone. These policies are independent of Monitor's PostgreSQL retention; a run can remain locally after its OpenSearch document expires, or vice versa.

OpenSearch / Analytics

Search log events by index

Open /opensearch/analytics. Select an index, enter a query, set time range and ordering, then select Search. The results table shows timestamp, level, message, service/project, and index. Expand a row to inspect its document JSON or copy it. You can set row count, move between pages, export the current result as JSON, refresh, or enable 30-second auto-refresh.

The general log-events view offers a Field filters builder for OpenSearch document fields. For example, select kestrel-application-logs, enter query ERROR, choose Past 24 Hours, and search. A field filter such as level.keyword=ERROR applies to that index only when the field exists in its mapping.

i
Choose the execution index for Logger run search

When kestrel-execution-logs is selected, Analytics uses a transaction dashboard with a dedicated Custom fields panel. Logger custom-field filtering belongs there, not in the generic field-filter builder for unrelated indices.

Execution transactions

Search runs and inspect ordered steps

Select kestrel-execution-logs in Analytics. Set a time range (15 minutes, 1 hour, 24 hours, 7 days, 30 days, or custom) and order. The dashboard summarizes matching transactions, success rate, failures, average duration, status distribution, execution volume, and recent issues. Below it, the transactions table shows timestamp, project, workflow, run ID, duration, and status. Expand a run to see its custom fields and ordered step timeline; expand a step for recorded details.

  1. In a workflow Logger, set customFields=[{"name":"OrderNo","value":"${pipeline.input.webHookRequest.queryparam.orderno}"}]. For an inbound orderno=123, the saved field is OrderNo=123.
  2. Select kestrel-execution-logs and a range containing the run. In Custom fields, enter name OrderNo and value 123; select Search. The transaction search uses the saved run metadata, including older indexed transactions without a custom-field token.
  3. To search an unknown prefix or suffix, use *123*. Add PoNo and 567 on a second row to require both fields. Matching is case-insensitive.
  4. Expand the result, verify OrderNo=123, then open the Logger step to read its message. Copy the run ID to find the same run under Monitor → Local Analytics.
Example search
Index:        kestrel-execution-logs
Time range:   Past 7 days
Custom field: OrderNo = *123*
Custom field: PoNo    = 567
Result:       one run containing both fields
Logger step:  Order 123 received

The query text at the top filters indexed documents. Custom fields, date range, and query all narrow the results. OpenSearch must contain the execution document; the PostgreSQL run alone cannot create a missing OpenSearch result. Dashboard figures reflect the current matching query and range, not every run in the platform.

Diagnosis

When logs or transactions do not appear

SymptomNext check
No indices listedVerify saved Configuration, successful connection test, backend access to OpenSearch, and whether any log documents have been indexed.
Run exists in Local Analytics but not hereSelect kestrel-execution-logs, widen the range, search *, check indexing health and OpenSearch retention. Compare the run ID.
Custom-field search returns no resultOpen the local run and confirm the actual saved field name/value; use the same time range in both views; verify the OpenSearch execution document still exists.
Wrong certificate or authentication errorTest the exact endpoint and credentials from Kestrel's backend host. For TLS, ensure the chosen Keystore alias contains the correct issuing certificate.
Counts differ between viewsCheck filter scope, ingestion delay, and independent PostgreSQL/OpenSearch retention. Local Analytics and OpenSearch read different stores.

For worker queues and publication pressure, use Administration → Runtime Operations. For the message and metadata contract, use the Logger connector guide.

Developer reference

How the Analytics page queries Kestrel

The browser calls Kestrel's authenticated /api/opensearch API, never the cluster directly. Configuration uses GET /configuration, administrator-only POST /configuration/test and PUT /configuration; log deletion uses administrator-only PUT /configuration/retention. Analytics lists indices with GET /indices and searches general documents with POST /search. Execution transactions use POST /execution-transactions/search, POST /execution-transactions/dashboard, and GET /execution-transactions/{runId}/steps?index=kestrel-execution-logs.

POST /api/opensearch/execution-transactions/search
Content-Type: application/json

{
  "index": "kestrel-execution-logs",
  "query": "*",
  "timeField": "@timestamp",
  "fromTime": "2026-10-18T00:00:00Z",
  "toTime": "2026-10-19T00:00:00Z",
  "filters": {"customFields.OrderNo": "*123*"},
  "sortField": "@timestamp",
  "sortOrder": "desc",
  "page": 0,
  "size": 50
}

The backend checks saved run metadata for the custom-field predicate, then restricts OpenSearch to matching run IDs. This lets a transaction document indexed before the custom-field token was added still match if its run record remains in PostgreSQL. OpenSearch must still have the transaction document. Returned transactions include run status, timing, project/workflow names, run ID, and saved custom fields; the steps endpoint supplies ordered detail on expansion.
