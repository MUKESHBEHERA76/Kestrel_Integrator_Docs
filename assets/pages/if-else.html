Project / Reusable Service / IF-ELSE

Run different service steps based on pipeline data.

IF-ELSE evaluates ordered conditions. It runs the children of the first matching IF or ELSE IF branch, otherwise it runs the optional ELSE branch, and then continues with the steps after the condition group.

What IF-ELSE does

Choose one execution branch

Use IF-ELSE when a reusable service must perform different operations for different runtime values.

The editor stores the complete structure inside an IF condition Group. The group contains one IF, zero or more ELSE IF branches, and at most one ELSE branch.

BranchConditionWhen it runs
IFRequired for useful branchingEvaluated first. Its child steps run when the expression is true.
ELSE IFRequiredEvaluated in displayed order only when every earlier condition was false.
ELSENoneRuns only when IF and every ELSE IF are false.
i
Only one branch runs

After the first true condition is found, remaining ELSE IF conditions are not evaluated. ELSE is the fallback and always remains last.

Condition expressions

Compare pipeline values using boolean expressions

The condition editor accepts pipeline paths, literal values, comparison operators, logical operators, and parentheses.

FeatureSyntaxExample

Numeric or ordered comparison>, >=, <, <=${pipeline.input.order.total} >= 1000
AND&&${pipeline.input.enabled} == true && ${pipeline.input.region} == 'IN'

String literalSingle or double quotes${pipeline.input.type} == "PRIORITY"
Boolean literaltrue, false${pipeline.input.customer.vip} == true

Truth-only conditions

A pipeline path can be used without a comparison. Boolean true, a non-zero numeric value, a non-empty String, and a non-empty List are true. Null, Boolean false, numeric zero, an empty String, and an empty List are false. Text such as "false" or "0" is still a non-empty String, so compare it explicitly when the input type is String.

${pipeline.input.enabled}

${pipeline.input.order.total} >= 1000

(${pipeline.input.customer.vip} == true) &&
(${pipeline.input.order.status} != 'CANCELLED')
!
An empty condition evaluates to false

Always define IF and ELSE IF conditions before testing. Invalid syntax raises a CONDITION_ERROR at runtime.

ELSE IF and ELSE

Add and order additional branches

  1. 1
    Select the root IF

    Branch actions are available from the IF row and its Properties panel.

  2. 2
    Add ELSE IF when another condition is needed

    Define its Comment and Condition exactly like the root IF.

  3. 3
    Add ELSE IF branches in evaluation order

    Branches are evaluated in their displayed order. Plan the most specific or highest-priority condition first; remove and add a branch again if its order must change.

  4. 4
    Add ELSE when a fallback is required

    Only one ELSE is created, it has no condition, and it stays after every ELSE IF.

If no condition matches and no ELSE exists, the group performs no child work and execution continues with the next step after the group.

Steps inside branches

Each branch can contain its own ordered implementation

IF, ELSE IF, and ELSE are containers. Their child steps run only when that branch is selected.

  1. 1
    Select the branch

    Choose IF, an ELSE IF, or ELSE in the flow tree.

  2. 2
    Add a child

    Use the branch's Add child action to create a Map pipeline child, or drag a Flow/Utils item onto the branch and drop it inside.

  3. 3
    Add more steps

    A branch can contain mappings, utilities, project-service calls, loops, TRY/CATCH, process groups, and other supported flow steps.

  4. 4
    Order the children

    Use drag-and-drop, Move up/down, Nest, and Outdent to create the intended hierarchy.

  5. 5
    Map data in child steps

    The IF control item itself does not expose pipeline mapping. Select each child step to map its inputs and outputs.

IF condition Group
├── IF  (total >= 1000)
│   ├── Map pipeline: approvalStatus = MANUAL_REVIEW
│   └── Project service: createApprovalTask
├── ELSE IF  (total >= 100)
│   └── Project service: runFraudScreening
└── ELSE
    └── Map pipeline: approvalStatus = AUTO_APPROVED

Map pipeline: build final service response

The final MAP step is outside the condition group, so it runs after whichever branch was selected.

Real use case

Choose an order-approval path

A reusable service receives an order and customer risk information. It must select one approval path.

Input values

{
  "order": {
    "total": 1250,
    "status": "NEW"
  },
  "customer": {
    "vip": false,
    "blocked": false
  }
}
BranchCommentConditionChild work
IFBlocked customers cannot continue${pipeline.input.customer.blocked} == trueEXIT with an exception or map a rejected result.
ELSE IFHigh-value orders require manual approval${pipeline.input.order.total} >= 1000Set status to MANUAL_REVIEW and call an approval-task service.
ELSE IFVIP orders use expedited approval${pipeline.input.customer.vip} == trueSet status to EXPEDITED.
ELSEAll remaining valid orders use standard approvalNoneSet status to STANDARD.

For the displayed input, the high-value ELSE IF is the first true condition, so its children run and later branches are skipped.

Good practices

Keep conditions understandable and safe

  • Use Comments to explain the business decision, not to repeat the expression.
  • Put narrow or high-priority ELSE IF conditions before broad conditions.
  • Use parentheses when combining && and ||.
  • Compare strings with quotes and compare missing values with $null.
  • Create complex values in an earlier MAP or utility step, then keep the IF expression short.
  • Do not put the same side-effecting service call in multiple branches unless that duplication is intentional.
  • Use ELSE only when a default behavior is safe. Otherwise allow no branch to run and handle the result explicitly afterward.
  • Test IF, every ELSE IF, ELSE, null values, boundary numbers, and empty lists before callers depend on the service.
