Workflow triggers / AMQP 1.0

Start a workflow from an AMQP 1.0 source.

AMQP 1.0 Trigger attaches to an existing broker destination and starts a workflow when a message arrives. It reads from a project AMQP 1.0 connection, provides the message in the pipeline, and acknowledges it after successful execution.

Setup

Configure an AMQP 1.0 consumer

  1. 1
    Get the source address

    Have the broker administrator provide an existing queue, topic, or generic source address, plus permission to attach a consumer. The exact address syntax is provider-specific.

  2. 2
    Create the connection

    Follow Create an AMQP 1.0 connection. Test protocol negotiation and authentication, then save and enable it.

  3. 3
    Add the trigger

    Drag AMQP 1.0 Trigger from workflow triggers onto the canvas and connect it to the first processing step. Do not add a second trigger to the same workflow.

  4. 4
    Choose destination and processing

    Double-click the trigger. Select the AMQP 1.0 connection, Destination type (Queue, Topic, or Generic address), and enter the existing Source address. Set processing mode, delivery mode, and flow control.

  5. 5
    Save, enable, and test

    Resolve workflow warnings, save and enable the workflow, then publish a test message to the configured source. Inspect the workflow run and broker delivery state.

Pipeline contract

Use the received body and metadata

Each delivery starts a run with ${pipeline.input.AMQP_Response}. Single mode contains one message document; batch mode contains AMQP_Response.messages[]. The trigger also sets ${pipeline.input.messageCount} (Integer) and ${pipeline.input.timedOut} (Boolean). An idle poll does not create an empty workflow run.

Field under AMQP_ResponseTypeMeaning
body.messageStringText representation of the message body.
body.bytesStringBase64 representation of message bytes.
headersDocumentApplication properties exposed as headers.
propertiesDocumentAvailable JMS/AMQP metadata: messageId, correlationId, replyTo, type, timestamp, expiration, priority, redelivered, destination.
messages[]DocumentListOnly in batch mode; each item has body, headers, and properties.

Map these from pipeline in to downstream steps. The trigger does not validate message payload structure; add a parser or Schema Validator when the business flow requires one.

Example

Consume an order message

Create AMQP 1.0 connection OrdersAmqp10 with the broker's actual endpoint and credentials. Have the broker administrator provide source address orders.incoming and consumer permission. Configure AMQP 1.0 Trigger with Connection OrdersAmqp10, Destination type Queue, Source address orders.incoming, Processing Serial, and Delivery Single message.

Broker body:    {"orderId":"ORD-1042","total":89.50}
Pipeline path:  ${pipeline.input.AMQP_Response.body.message}
Next steps:     parse JSON → validate order → process order

For a broker topic, select Topic and use the address supplied by that broker. Topic subscription and durability behavior depend on the broker; verify them with a restart and redelivery test before production use.

Delivery semantics

When a message is settled

Kestrel keeps the delivery unsettled while the workflow runs. On Success, it acknowledges the message. On failure, it releases or recovers the delivery for redelivery. A broker may deliver a message again, so downstream effects should be idempotent. Trigger consumers are started only for enabled workflows.

Concurrent mode scales through multiple consumer slots, subject to instance capacity and broker support for competing consumers. The application retries receive and connection failures; inspect application logs and workflow execution details when the broker is reachable but no run appears.

SymptomCheck
Connection warningSelect a saved, enabled AMQP 1.0 connection from the same project.
