Execution architecture

How a Kestrel project becomes a running integration.

Designs are stored and versioned in PostgreSQL, compiled into immutable plans, admitted durably through RabbitMQ, and executed by independent workers. This guide follows the complete path from saving an artifact to searching its logs.

Runtime architecture

The complete production path

Clients enter through control-plane API nodes. Durable commands cross RabbitMQ to execution workers, while detailed masked logs take a separate asynchronous path through observability workers to OpenSearch.

!
No silent production fallback

If RabbitMQ cannot provide durable admission, a production API returns 503 Service Unavailable. It does not execute the workflow locally.

Design-time lifecycle

How a saved project artifact reaches every runtime node

A workflow is never executed directly from an editable UI document. Saving creates a durable version, then every API and worker compiles the committed definition.

  1. 1
    Save and version

    The same PostgreSQL transaction stores the artifact change, creates its next monotonically increasing version, and writes an integration-change outbox event.

  2. 2
    Publish the committed change

    The outbox publisher sends a confirmed event to the ki.integration.events fanout exchange. An uncommitted edit can never be published.

  3. 3
    Compile on each node

    Every API and worker validates the graph, mappings, connector definitions, reusable-service references, and subworkflows before atomically replacing its local plan.

  4. 4
    Admit only valid current plans

    Invalid artifacts are marked unavailable without taking down the node. Disabled workflows are removed from new admission; reusable services remain invokable when valid.

  5. 5
    Repair missed events

    A 60-second reconciliation compares local versions with PostgreSQL and reloads anything missed while a node or broker connection was unavailable.

Runtime lifecycle

What happens when a workflow runs

Every authorized trigger source converges on the same durable admission and worker pipeline. Trigger adapters are extensible; the listed sources are examples, not a closed set.

TriggerAny authorized source
AdmissionAuthorize + resolve plan
TransactionCreate run + outbox
TransportConfirmed RabbitMQ publish
ExecutionClaim, lease, run, finalize
  1. 1
    Authenticate and authorize

    The control-plane API checks the caller, project permission, workflow enabled state, input size, and platform overload limits.

  2. 2
    Resolve an immutable plan

    The API resolves the exact artifact version from JVM memory. updatedAt is not a version authority.

  3. 3
    Write run and command atomically

    One short PostgreSQL transaction creates the execution in ACCEPTED state and its versioned outbox command with unique runId and commandId.

  4. 4
    Publish durably

    A publisher claims the outbox row, sends a persistent message, waits for RabbitMQ confirmation, and only then marks the command published and the run QUEUED.

  5. 5
    Claim on one worker

    A worker receives with manual acknowledgement, atomically claims the PostgreSQL run, obtains its distributed lease, and restores the exact plan version if it is not already cached.

  6. 6
    Execute within bounds

    The bounded dispatcher runs steps, nested reusable services, and initial subworkflows in the same worker event and execution context. Connector bulkheads isolate HTTP, JDBC, file, and transformation capacity.

  7. 7
    Heartbeat and observe

    The worker renews ownership every 10 seconds by default, checks cancellation between steps, updates progress, and emits masked log events asynchronously.

  8. 8
    Commit, then acknowledge

    The terminal outcome is committed to PostgreSQL before the RabbitMQ delivery is acknowledged. A crash before acknowledgement is recovered without changing execution identity.

Execution contract

The command carries identity, not mutable runtime state

Commands are explicitly versioned and point to the exact artifact revision. Secrets are never embedded in the transport envelope.

  "schemaVersion": 1,
  "commandId": "uuid",
  "runId": "uuid",

  "artifactVersion": 12,
  "projectId": "uuid",
  "source": "MANUAL",
  "contextId": "string",
  "acceptedAt": "timestamp",

  "payloadReference": null,
  "traceContext": {}

runId

The durable, user-visible identity retained through recovery.

commandId

The immutable transport idempotency identity with a unique database constraint.

artifactVersion

Pins the exact definition that must execute, even after a newer version is saved.

payloadReference

Points to shared storage when input is too large or binary; RabbitMQ carries its hash and metadata.

Reliability and recovery

At-least-once delivery without duplicate worker execution

Exactly-once behavior cannot be guaranteed across databases, queues, HTTP APIs, and arbitrary external systems. Kestrel makes redelivery safe and exposes the remaining side-effect boundary.

01

Atomic claim

A second worker cannot execute a run while its owner has a valid live lease.

02

Terminal check

A redelivered command for an already-terminal run is acknowledged without re-execution.

03

Lease recovery

An expired owner lease enters controlled recovery using the same run and command identities.

04

Business failure

Validation, mapping, connector, authentication, and workflow exceptions finish as FAILURE; they are not infrastructure dead letters.

05

Poison messages

Invalid schemas, corrupt payloads, missing versions, and exhausted crash recovery go to the execution dead-letter queue.

06

External writes

Connectors should pass business idempotency keys when supported because Kestrel cannot roll back a side effect committed before a worker crash.

Observability path

Execution metadata and detailed logs are stored separately

Keeping detailed step events out of the execution transaction protects throughput while preserving searchable diagnostics.

Authoritative metadata

Worker → PostgreSQL

Run identity, artifact/version, source, owner, current and final state, start/end/duration, failure code, and failure summary.

Detailed searchable events

Worker → RabbitMQ → Observability worker → OpenSearch

Logger output, pipeline-logger values, meaningful step failures, application events, and masked diagnostic snapshots.

✓
Mask before transport

Passwords, secrets, tokens, cookies, authorization values, API keys, private keys, and connector credentials are masked before an event enters RabbitMQ or OpenSearch.

Readiness and operations

A node serves traffic only when it can do so safely

API ready when

  • PostgreSQL and Flyway are ready
  • Artifact registry initial load is complete
  • JWT/security initialization is complete
  • RabbitMQ topology and publisher confirms are available

Worker ready when

  • PostgreSQL and RabbitMQ are reachable
  • The compiled-plan registry is loaded
  • Bounded executor and heartbeat are active
  • Required connector dependencies are initialized

Cluster coordination

  • Redis is required only when clustered correctness is configured
  • Redis loss stops new admissions/claims in required mode
  • Active work attempts safe PostgreSQL finalization
  • Health reports the dependency degradation
