Execution architecture

How a Kestrel project becomes a running integration.

Designs are stored and versioned in PostgreSQL, compiled into immutable plans, admitted durably through RabbitMQ, and executed by independent workers. This guide follows the complete path from saving an artifact to searching its logs.

Follow the message flow Follow a workflow run

API nodes admit work. Worker nodes execute it. PostgreSQL preserves the truth before, during, and after every run. Durable, versioned, horizontally scalable

Two different uses of RabbitMQ

The protected execution queue carries durable run commands. Logging queues carry observability events. An AMQP Trigger can also read a user-configured business queue; that input is converted into a Kestrel run before the execution queue is used.

Design rationale

Why each boundary exists

The architecture separates accepting work, delivering it, and performing it so that a slow connector does not hold the admission transaction open.

BoundaryPurposePractical effect
PostgreSQL run + outboxRecord the run and intent to publish atomically.A broker outage does not erase an accepted run; the publisher can retry from the committed outbox.
RabbitMQ execution queueBuffer admitted commands and deliver them to available workers.Short bursts need not start one thread per request. Queue depth and oldest age reveal when arrivals exceed processing.
Bounded worker concurrencyLimit active work and downstream pressure.More workers can increase parallelism until a connector, database, broker, or external API becomes the bottleneck.
Claim, lease, and manual acknowledgementCoordinate redelivery after failure.Only the owning worker should run the active execution; terminal state is recorded before acknowledging the message.
Pinned artifact revisionKeep each run on the version selected at admission.A workflow edit during a queued run does not change that run's plan.
Nested service executionShare pipeline context inside a parent run.Reusable services and callable subworkflows avoid an extra admission and queue round trip.
Separate logsKeep search and diagnostics off the execution state path.OpenSearch helps investigate runs while PostgreSQL remains the source of truth for their outcome.

Before the queue

Admission makes each accepted run durable

The API or trigger adapter checks whether the workflow can run, then creates the run and the message to be published.

  1. 1
    Validate the entry

    Check access, enabled state, the current compiled artifact, request limits, and required infrastructure. Different trigger adapters collect different inputs; all admitted top-level runs use the same execution contract.

  2. 2
    Pin the saved revision

    The command records the artifact ID and exact revision. Editing the workflow later cannot silently replace the version already assigned to a run.

  3. 3
    Commit run and outbox together

    A short PostgreSQL transaction writes an ACCEPTED execution run and a pending execution-outbox row. Each receives stable IDs, including a runId and a commandId.

  4. 4
    Return the run identity

    A caller can track that identity while publication and execution continue. A webhook can wait for its configured response window; if work continues beyond it, the caller can query the run by ID.

See Workflow for trigger configuration and Execution for the complete execution-state model.

RabbitMQ control

Queue the command without losing the database record

Kestrel publishes from the committed outbox, waits for broker confirmation, and lets bounded workers consume the protected queue.

StageWhat happensWhy it matters
Outbox publisherClaims pending rows, publishes persistent versioned commands with routing key workflow.execute, and waits for a publisher confirmation.Database commit and broker publish do not have to be one distributed transaction.
Protected queueThe execution command is delivered through ki.execution.workflow. Workers use bounded concurrency, prefetch, and manual acknowledgement.Bursts wait in the broker while worker and connector limits protect downstream systems.
Claim and leaseA worker claims the run in PostgreSQL and acquires a coordination lease before executing.Redelivery does not cause another live worker to execute the same run concurrently.
Finish and acknowledgeThe terminal result is saved before the broker delivery is acknowledged.A delivery interrupted by worker failure can be recovered using the same run identity.
!
The queue is a buffer, not unlimited capacity

If all workers are paused, draining, unavailable, or saturated, commands may wait. Watch queue message count, oldest age, outbox pending age, active executions, and dependency health in Runtime Operations.

Inside the worker

How workflow steps and services execute

The worker resolves the pinned plan and executes the topology in pipeline order. Connections and utilities are used by steps, while a reusable service is invoked from its parent workflow.

Failure boundaries

What the platform retries and what it cannot undo

Transport recovery and business operations have different guarantees.

Publisher failure

The outbox row remains recoverable for bounded retry. An exhausted publish attempt ends the run with a failure reason instead of leaving an invisible command.

Worker interruption

Claim and lease checks guard redelivery. A completed terminal run is not executed again merely because RabbitMQ redelivers its message.

Workflow failure

The worker records the failure outcome and error details. Error-handling branches can catch configured step failures before the run terminates.

External side effects

A remote API, email, or database outside Kestrel may have committed before a crash. Use destination idempotency keys or business deduplication where available.

Redis, when configured for clustered coordination, holds short-lived worker presence, leases, and control signals; it is not the durable run store. See Reliability for more detail.

Developer example

Webhook → validate → service → response

Consider an order workflow that validates an incoming request and calls a reusable service to calculate a price.

  1. 1
    Webhook receives an order

    The trigger captures headers, query parameters, body, and files into its pipeline. Kestrel admits a run and returns its runId.

  2. 2
    RabbitMQ delivers the command

    The publisher confirms the durable command; a worker claims it and loads the saved workflow revision.

  3. 3
    Workflow maps and validates

    Map webHookRequest.body to the validator input. The next step reads its mapped output.

  4. 4
    Call PriceService

    Map orderId and line items into the service inputs; the service calculates totals in a nested pipeline and returns its declared outputs to the parent.

  5. 5
    Respond and finish

    A response step sends the mapped result if the HTTP caller is still waiting. The worker records the terminal result, then acknowledges the queue delivery. Logs remain searchable separately.

Runtime architecture

The complete production path

Clients enter through control-plane API nodes. Durable commands cross RabbitMQ to execution workers, while detailed masked logs take a separate asynchronous path through observability workers to OpenSearch.

!
No silent production fallback

If RabbitMQ cannot provide durable admission, a production API returns 503 Service Unavailable. It does not execute the workflow locally.

Design-time lifecycle

How a saved project artifact reaches every runtime node

A workflow is never executed directly from an editable UI document. Saving creates a durable version, then every API and worker compiles the committed definition.

  1. 1
    Save and version

    The same PostgreSQL transaction stores the artifact change, creates its next monotonically increasing version, and writes an integration-change outbox event.

  2. 2
    Publish the committed change

    The outbox publisher sends a confirmed event to the ki.integration.events fanout exchange. An uncommitted edit can never be published.

  3. 3
    Compile on each node

    Every API and worker validates the graph, mappings, connector definitions, reusable-service references, and subworkflows before atomically replacing its local plan.

  4. 4
    Admit only valid current plans

    Invalid artifacts are marked unavailable without taking down the node. Disabled workflows are removed from new admission; reusable services remain invokable when valid.

  5. 5
    Repair missed events

    A 60-second reconciliation compares local versions with PostgreSQL and reloads anything missed while a node or broker connection was unavailable.

Runtime lifecycle

What happens when a workflow runs

Every authorized trigger source converges on the same durable admission and worker pipeline. Trigger adapters are extensible; the listed sources are examples, not a closed set.

TriggerAny authorized source
AdmissionAuthorize + resolve plan
TransactionCreate run + outbox
TransportConfirmed RabbitMQ publish
ExecutionClaim, lease, run, finalize
  1. 1
    Authenticate and authorize

    The control-plane API checks the caller, project permission, workflow enabled state, input size, and platform overload limits.

  2. 2
    Resolve an immutable plan

    The API resolves the exact artifact version from JVM memory. updatedAt is not a version authority.

  3. 3
    Write run and command atomically

    One short PostgreSQL transaction creates the execution in ACCEPTED state and its versioned outbox command with unique runId and commandId.

  4. 4
    Publish durably

    A publisher claims the outbox row, sends a persistent message, waits for RabbitMQ confirmation, and only then marks the command published and the run QUEUED.

  5. 5
    Claim on one worker

    A worker receives with manual acknowledgement, atomically claims the PostgreSQL run, obtains its distributed lease, and restores the exact plan version if it is not already cached.

  6. 6
    Execute within bounds

    The bounded dispatcher runs steps, nested reusable services, and initial subworkflows in the same worker event and execution context. Connector bulkheads isolate HTTP, JDBC, file, and transformation capacity.

  7. 7
    Heartbeat and observe

    The worker renews ownership every 10 seconds by default, checks cancellation between steps, updates progress, and emits masked log events asynchronously.

  8. 8
    Commit, then acknowledge

    The terminal outcome is committed to PostgreSQL before the RabbitMQ delivery is acknowledged. A crash before acknowledgement is recovered without changing execution identity.

Execution contract

The command carries identity, not mutable runtime state

Commands are explicitly versioned and point to the exact artifact revision. Secrets are never embedded in the transport envelope.

{
  "schemaVersion": 1,
  "commandId": "uuid",
  "runId": "uuid",
  "artifactId": "uuid",
  "artifactVersion": 12,
  "projectId": "uuid",
  "source": "MANUAL",
  "contextId": "string",
  "acceptedAt": "timestamp",
  "input": {},
  "payloadReference": null,
  "traceContext": {}
}
runId

The durable, user-visible identity retained through recovery.

commandId

The immutable transport idempotency identity with a unique database constraint.

artifactVersion

Pins the exact definition that must execute, even after a newer version is saved.

payloadReference

Points to shared storage when input is too large or binary; RabbitMQ carries its hash and metadata.

Reliability and recovery

At-least-once delivery without duplicate worker execution

Exactly-once behavior cannot be guaranteed across databases, queues, HTTP APIs, and arbitrary external systems. Kestrel makes redelivery safe and exposes the remaining side-effect boundary.

01

Atomic claim

A second worker cannot execute a run while its owner has a valid live lease.

02

Terminal check

A redelivered command for an already-terminal run is acknowledged without re-execution.

03

Lease recovery

An expired owner lease enters controlled recovery using the same run and command identities.

04

Business failure

Validation, mapping, connector, authentication, and workflow exceptions finish as FAILURE; they are not infrastructure dead letters.

05

Poison messages

Invalid schemas, corrupt payloads, missing versions, and exhausted crash recovery go to the execution dead-letter queue.

06

External writes

Connectors should pass business idempotency keys when supported because Kestrel cannot roll back a side effect committed before a worker crash.

Observability path

Execution metadata and detailed logs are stored separately

Keeping detailed step events out of the execution transaction protects throughput while preserving searchable diagnostics.

Authoritative metadata

Worker → PostgreSQL

Run identity, artifact/version, source, owner, current and final state, start/end/duration, failure code, and failure summary.

Detailed searchable events

Worker → RabbitMQ → Observability worker → OpenSearch

Logger output, pipeline-logger values, meaningful step failures, application events, and masked diagnostic snapshots.

✓
Mask before transport

Passwords, secrets, tokens, cookies, authorization values, API keys, private keys, and connector credentials are masked before an event enters RabbitMQ or OpenSearch.

Configuration is not a capacity guarantee

Supported throughput and autoscaling thresholds are established through Phase 6 load, spike, soak, restart, drain, and dependency-failure testing. Kestrel does not advertise “unlimited” capacity.

Readiness and operations

A node serves traffic only when it can do so safely

API ready when

  • PostgreSQL and Flyway are ready
  • Artifact registry initial load is complete
  • JWT/security initialization is complete
  • RabbitMQ topology and publisher confirms are available

Worker ready when

  • PostgreSQL and RabbitMQ are reachable
  • The compiled-plan registry is loaded
  • Bounded executor and heartbeat are active
  • Required connector dependencies are initialized

Cluster coordination

  • Redis is required only when clustered correctness is configured
  • Redis loss stops new admissions/claims in required mode
  • Active work attempts safe PostgreSQL finalization
  • Health reports the dependency degradation
Implementation status

Throughput planning

Target: 10,000+ completed runs per second

This is a proposed platform-wide target, equal to at least 600,000 completed top-level runs per minute. A nested service call is part of its parent run. There is no verified production throughput rating yet; accepted runs and completed runs must be measured separately.

The local validation recorded 60 successful executions and 60 confirmed outbox publications, but did not establish sustained capacity. The validation runbook proposes a 25-admissions-per-second load hold (1,500 offered admissions/minute) and a 100-admissions-per-second spike (6,000 offered admissions/minute). Those are test inputs, not demonstrated or guaranteed throughput.

i
Illustrative calculation, not a Kestrel benchmark

If four workers each sustain ten active runs, and each run occupies a slot for two seconds on average, the slot-only estimate is 4 × 10 × 60 ÷ 2 = 1,200 completed runs/minute. The real rate can be lower because database writes, outbox publishing, broker delivery, connector limits, external API latency, retries, and workflow branches consume capacity. A ten-second average run under the same assumptions yields only 240/minute.

For a deployment estimate, measure sustained completion rate while the oldest queue age and outbox pending age return to baseline. Repeat the candidate rate, inspect p95 admission latency, worker saturation, PostgreSQL and RabbitMQ health, external dependency limits, error rate, and recovery after a spike. Apply headroom below the highest repeatable rate. The Scaling section describes operational metrics and the validation runbook defines the test gates.

!
Deployment size alone cannot establish this rate

A single large VM may still be limited by PostgreSQL durability, RabbitMQ confirms, network latency, or external systems. The target needs production-like mixed-workload tests across webhook, scheduler, and event triggers, plus failure and recovery tests. Until those pass, do not use 10,000/s as a supported capacity statement.
