Google Pub/Sub connector

Choose one of 13 operations, map PubSub_Request inputs, and use PubSub_Response outputs downstream.

Configure and map the step

Go to Projects → your project → Workflows → open a workflow. Drag Google Pub/Sub from Connectors onto the canvas. Open the step and choose a tested, enabled Google Pub/Sub Connection and an Operation. The Operation changes the Step In fields under PubSub_Request. Open Pipeline settings and map those fields from the preceding step or hardcode a fixed example value. Map PubSub_Response fields to Pipeline Out for the next step, then save and run the workflow.

The project identifier and service key are stored in the connection. They are not pipeline fields. Every request input shown here is a String, including numeric text and JSON text. JSON string fields can contain pipeline variable substitutions before runtime parsing. The root PubSub_Request and PubSub_Response are Document containers grouping those String fields.

Pull is synchronous for one request. A missing receivedMessages array means no messages were returned. Use ackIdsJson after successful processing; use NACK for redelivery when appropriate. This connector does not run a continuous Pub/Sub trigger, and pull does not ACK automatically. Design processing to tolerate duplicate deliveries.

Pull messages · PULL_MESSAGES

Step In: PubSub_Request fields: subscriptionId; maxMessages optional. No automatic ACK. Decode each message.data from Base64 and use ackId in ACK or NACK.

}

Troubleshooting and limits

  • HTTP 401: check service account key validity in the connection.
  • HTTP 403: enable the API and grant the selected action’s IAM role on the target resource.
  • HTTP 404: verify project, bucket/dataset/topic, and item IDs. The connection target project determines the request project.
  • When using optional page tokens, pass Google’s returned nextPageToken into the next invocation. Stop when it is absent.
  • All Google API errors fail the step and can be inspected in workflow execution logs.

Publish, pull, and acknowledge example

  1. Choose Publish message. Set topicId = orders-created, message = {"poid":"1234"}, and attributesJson = {"source":"kestrel"}. Pub/Sub stores message data as Base64; Kestrel encodes the String.
  2. In another workflow step choose Pull messages with subscriptionId = orders-worker and maxMessages = 10. Parse PubSub_Response.body to inspect each receivedMessages[].message; decode message.data from Base64.
  3. After processing succeeds, map PubSub_Response.ackIdsJson into an ACK step's PubSub_Request.ackIdsJson. If processing fails and you want immediate redelivery, map the same JSON array into a NACK step. Do not use message.messageId as an ACK ID.

Google references: topics.publish, subscriptions.pull, subscriptions.acknowledge, and modifyAckDeadline for NACK.
