Before you begin

Prepare the broker and connection

  1. 1
    Prepare a destination

    Have the broker administrator create the queue, topic, or address and grant the connection account publish or consume permission. Kestrel does not create broker destinations.

  2. 2
    Create the connection

    Follow the AMQP 1.0 connection guide. Test, save, and enable connection OrdersAmqp10 in the workflow project. The connection test verifies broker login, not destination permissions.

  3. 3
    Add the connector

    Drag AMQP 1.0 from the workflow Connector tab, wire it into the path, then double-click it. Select connection OrdersAmqp10 and choose Publish or Subscribe.

  4. 4
    Map and test

    Open Settings to map the operation's pipeline fields, save the workflow, and run it with a test payload. Inspect step output and broker delivery.

Use the matching protocol listener: this connector speaks AMQP 1.0.

Publish operation

Send a message to an existing destination

Set Operation to Publish, Destination type to Queue, and Queue or topic / Target address to orders.incoming. Select the project connection OrdersAmqp10.

Choose Queue, Topic, or Generic address according to the broker destination. Enter its exact target/source address. For Publish, choose persistent delivery and an optional time to live in milliseconds. AMQP 1.0 does not expose the AMQP 0-9-1 exchange or routing key fields.

In pipeline Settings, map a text payload to ${pipeline.input.AMQP_Request.body.message}, for example:

{"orderId":"ORD-1042","total":89.50}

Or map Base64 data to ${pipeline.input.AMQP_Request.body.bytes} for binary content. If bytes is set, it takes precedence over message; invalid Base64 fails the step. You may map headers and supported properties such as message ID, correlation ID, and type. For a JSON text body, set a content-type property where supported by the protocol and consumer.

On success, ${pipeline.output.AMQP_PublishResult} is a Document, for example:

{"published":true,"destination":"orders.incoming","timestamp":"2026-10-15T10:00:00Z"}

Published means the connector's send operation completed; it does not mean a downstream consumer processed the message.

Subscribe operation

Receive during an existing run

Choose Subscribe, the matching destination type, and existing queue/source orders.incoming. Set Receive mode to Single message or Multiple messages. Batch size is 1–1000; Receive timeout is in milliseconds (maximum 300000, default 30000). A timeout with no delivery returns messageCount = 0 and timedOut = true; it does not fail the workflow by itself.

Subscribe has no Step In document. In single mode, ${pipeline.output.AMQP_Response} contains one message. In batch mode it contains messages, a list of message documents. Map the response body into a parser, validator, or business step.

{"body":{"message":"{\"orderId\":\"ORD-1042\"}","bytes":"eyJvcmRlcklkIjoiT1JELTEwNDIifQ=="},"headers":{},"properties":{"destination":"orders.incoming"}}

The exact headers and properties depend on what the producer and broker supply. Use body.bytes for binary payloads; body.message is a UTF-8 text view.

Delivery and failures

Understand acknowledgement and retry behavior

For Subscribe, Kestrel holds a received delivery until the workflow run completes. It acknowledges after success and requests redelivery after failure. A workflow that handles an error and still finishes successfully is treated as success. Brokers can redeliver after a crash or connection loss; design downstream updates to be idempotent.

A publish or receive error fails the connector step and can be caught by the workflow Exception Handler. Check the workflow execution log and broker logs for authentication, destination permission, routing, or timeout errors. A successful connection test does not verify a destination.

For the event-driven alternative and its concurrency settings, see AMQP 1.0 Trigger. For transport, TLS, and authentication settings, see the connection guide.
