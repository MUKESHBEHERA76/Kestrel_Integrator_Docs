Workflow / Connectors / Google Cloud Storage

Google Cloud Storage connector

Choose one of 11 operations, map Gcs_Request inputs, and use Gcs_Response outputs downstream.

Configure and map the step

Go to Projects → your project → Workflows → open a workflow. Drag Google Cloud Storage from Connectors onto the canvas. Open the step and choose a tested, enabled Google Cloud Storage Connection and an Operation. The Operation changes the Step In fields under Gcs_Request. Open Pipeline settings and map those fields from the preceding step or hardcode a fixed example value. Map Gcs_Response fields to Pipeline Out for the next step, then save and run the workflow.

The project identifier and service key are stored in the connection. They are not pipeline fields. Every request input shown here is a String, including numeric text and JSON text. JSON string fields can contain pipeline variable substitutions before runtime parsing. The root Gcs_Request and Gcs_Response are Document containers grouping those String fields.

For object names containing slashes, map the full name such as orders/1234.json; Kestrel URL-encodes it. Upload and download accept/return Base64 content, each limited to 10 MiB inline. For larger files, use a transfer design outside these inline operations.

Operation examples

The following examples use illustrative values. Actual Google responses include additional fields. Operation details and IAM requirements: Google REST API reference.

Create bucket · CREATE_BUCKET

Step In: Gcs_Request fields: bucket, location; storageClass optional. Creates a project bucket; bucket names are globally unique.

Example mapped request:

{
  "Gcs_Request": {
    "bucket": "acme-orders-archive",
    "location": "US",
    "storageClass": "STANDARD"
  }
}

Illustrative Google response in Gcs_Response.body:

{
  "name": "acme-orders-archive",
  "location": "US"
}

Named Step Out: name; location. Most actions expose Gcs_Response.body as JSON text; Download object returns contentBase64 and sizeBytes instead. Fields appear only when present in the Google response.

Troubleshooting and limits

  • HTTP 401: check service account key validity in the connection.
  • HTTP 403: enable the API and grant the selected action’s IAM role on the target resource.
  • HTTP 404: verify project, bucket/dataset/topic, and item IDs. The connection target project determines the request project.
  • When using optional page tokens, pass Google’s returned nextPageToken into the next invocation. Stop when it is absent.
  • All Google API errors fail the step and can be inspected in workflow execution logs.

End-to-end object example

  1. Create the Cloud Storage connection and grant the service account permissions on the bucket.
  2. Map a webhook request's webHookRequest.body through a Base64 encoding utility into Gcs_Request.contentBase64. Set bucket = acme-orders-archive, objectName = orders/${pipeline.input.orderId}.json after extracting orderId from the webhook JSON into a runtime variable, and contentType = application/json.
  3. Choose Upload object. Map Gcs_Response.name to the next step or read the full metadata from Gcs_Response.body.
  4. For a download, use the same bucket and object name. Decode Gcs_Response.contentBase64 before treating the result as UTF-8 JSON or binary data.

Google references: objects.insert, objects.get, and Storage IAM roles.
