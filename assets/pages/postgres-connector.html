Workflow / Connectors / PostgreSQL

Execute PostgreSQL SQL in a workflow

Run one SQL statement using an enabled project PostgreSQL connection. Map queryString into the step and route its two outputs to later steps.

Step setup

Configure the connector

  1. 1
    Create and test the connection

    Follow the PostgreSQL connection guide; keep the project connection enabled.

  2. 2
    Add the workflow step

    Drag the PostgreSQL connector from the connector palette and connect it to the execution path. Double-click it and select the project connection.

  3. 3
    Configure execution

    Set Retry Count, Retry Interval in seconds, and optional Query Time Out in seconds. Retry Count 0 means one attempt; use retries carefully for writes.

  4. 4
    Map the pipeline

    In settings, map a SQL string into ${pipeline.input.queryString}. Map resultCount and dbResponse from Step Out to the next step as needed. Save the mapping and workflow.

Pipeline contract

Input and output variables

VariableTypeUse
${pipeline.input.queryString}StringRequired; one SQL statement. Runtime pipeline substitution inserts text, not bound JDBC parameters.
${pipeline.output.resultCount}StringNumber of returned rows for SELECT, or affected row count for DML.
${pipeline.output.dbResponse}StringSerialized JSON with resultList; column labels map to string values, SQL NULL to JSON null.

For statements without a result set, dbResponse contains {"resultList":[]}. A SELECT reads the returned result set into memory; keep result sets bounded with a WHERE clause or database-specific row limit.

SQL examples

Read and update an order

Map this read statement to queryString:

SELECT id, status FROM public.orders WHERE id = 1042

For one row, the step returns resultCount = "1" and a dbResponse string such as:

{"resultList":[{"id":"1042","status":"NEW"}]}

A later step can parse this JSON string if it needs a structured document. For a write, map a single update statement:

UPDATE public.orders SET status = 'SHIPPED' WHERE id = 1042

If one row changes, resultCount is "1" and dbResponse is {"resultList":[]}. Column label casing follows the JDBC driver and SQL aliases. Build SQL from trusted values; text substitution does not escape user input and is unsuitable for untrusted values.

Transactions

Commit on success; roll back on workflow failure

The runtime opens each PostgreSQL JDBC connection with auto commit disabled and reuses it for steps that select the same connection during a workflow run. When the workflow run completes successfully, Kestrel commits its pending JDBC work. If the run exits with a failure, timeout, or cancellation, Kestrel attempts to roll back pending JDBC work. You do not need to add a separate COMMIT step for ordinary DML.

An Exception Handler that catches an error and lets the workflow finish successfully leads to commit. To roll back, the run must finish in a failed state. This is a transaction on each database connection, not one atomic transaction across multiple databases, HTTP calls, messages, or email. Some database commands, especially DDL, may commit implicitly according to the database; use transactional DML for rollback-dependent flows. If one connection's commit fails after another has already committed, Kestrel cannot undo the earlier commit.

Troubleshooting

Diagnose execution errors

SymptomCheck
Connection unavailableIt belongs to this project, is enabled, and passes the connection test.
Missing queryStringMap a nonempty SQL statement to Step In.
SQL or permission errorCheck table/schema names, SQL dialect, and privileges of the selected credential.
Timeout or retryInspect the original database error and query timeout. A retry of non-idempotent SQL may repeat work if the first attempt reached the database.
