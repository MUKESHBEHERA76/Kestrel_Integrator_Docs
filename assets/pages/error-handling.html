Recover from service errors with TRY, CATCH, and FINALLY.

Protect failure-prone steps in TRY, use the paired CATCH to inspect and handle the runtime error, and reserve the FINALLY branch for cleanup that must run regardless of the outcome.

Error-handling model

Keep the normal path separate from recovery and cleanup

PartWhen it runsUse it for
TRYDuring normal executionConnector calls, utility steps, mappings, service calls, validation, and other work that can fail.
CATCHOnly when the paired TRY raises an integration runtime errorLogging, creating a safe error response, compensating work, or converting a technical failure into a business result.
FINALLYAfter TRY and any CATCH handlingCleanup that must happen after success, handled failure, or an error that continues outward.
i
CATCH handles runtime failures, not ordinary business branches

Use IF-ELSE or Switch Case for expected decisions. Use TRY/CATCH for failures raised by execution.

Create a handler

The editor creates TRY and CATCH as one pair

Selecting either TRY or CATCH from the Flow library creates both steps with the same generated Pair name.

  1. 1
    Open the Flow tab

    In the reusable service editor, find TRY or CATCH in the Flow step library.

  2. 2
    Add the pair

    Click or drag either item. The editor creates a TRY and its paired CATCH automatically.

  3. 3
    Keep both at the same level

    The runtime pairs them by Pair name and parent container. Their Pair name is generated and read-only.

  4. 4
    Add child steps

    Place normal work inside TRY and recovery work inside CATCH. Use Comments to explain the protected operation and recovery intent.

  5. 5
    Test success and failure

    Confirm the normal route skips CATCH and a forced failure produces the expected recovery result.

!
Do not separate or delete one half of a pair

A CATCH is selected only when its Pair name and parent level match the TRY. Keeping the generated pair intact avoids unhandled or legacy fallback behavior.

TRY branch

Put only the protected work inside TRY

  • TRY executes its child steps in their displayed order.
  • When all children succeed, the paired CATCH is skipped.
  • When a child raises an integration runtime error, remaining TRY children are skipped and the paired CATCH begins.
  • Connector, utility, mapping, nested service, and exceptional EXIT failures can be handled by CATCH when they are reported as runtime errors.
  • Keep work that must run after both success and failure out of the normal TRY branch; place it in the FINALLY branch.
TRY  (pair: try-catch-1)
├── Map pipeline: build request
├── Invoke service or utility
└── Map pipeline: build success output

CATCH  (pair: try-catch-1)
└── Map pipeline: build safe error output

CATCH branch

Recover, compensate, or prepare an error response

  • CATCH runs only for a failure raised from its paired TRY.
  • The runtime exposes a temporary ${pipeline.output.errorDoc} while CATCH children execute.
  • If CATCH finishes normally, the original failure is considered handled and execution continues after the TRY/CATCH structure.
  • If a CATCH child fails, the new runtime error propagates to an enclosing TRY/CATCH or to the service caller.
  • Map any error information needed later into Service Output or another durable pipeline variable before CATCH finishes.
!
Do not return internal stack traces to API consumers

Use the stack trace for controlled diagnostics. Build a safe public message and correlation identifier for external responses.

CATCH input

Read the temporary errorDoc document

The CATCH pipeline exposes these String fields.

Pipeline pathMeaning
${pipeline.output.errorDoc.errorMessage}The runtime failure message.
${pipeline.output.errorDoc.stepName}The step associated with the failure.
${pipeline.output.errorDoc.errorStackTrace}The server-side stack trace for diagnostics.
${pipeline.output.errorDoc.timestamp}The UTC instant at which the error details were recorded.
 
Map inside CATCH

${pipeline.output.errorDoc.errorMessage}
    -> ${pipeline.output.result.message}

${pipeline.output.errorDoc.stepName}
    -> ${pipeline.output.result.failedStep}

Hardcode "FAILED"
    -> ${pipeline.output.result.status}

The runtime removes errorDoc when CATCH completes. See Map Pipeline and Pipeline Sub for mapping and path syntax.

FINALLY branch

Run cleanup after every TRY outcome

The execution engine runs direct children of TRY whose Branch property is finally. Use this for cleanup, final audit logging, or resetting temporary pipeline state.

  1. 1
    Add the cleanup step under TRY

    Place the mapper, utility, logger, or other cleanup operation as a child of the TRY container.

  2. 2
    Select the cleanup child

    In the Properties panel, set its Branch value to finally.

  3. 3
    Keep cleanup safe

    FINALLY runs after success, after handled failure, and while an error or normal EXIT is propagating outward.

!
FINALLY is structural, not positional

A standalone FINALLY row is not associated with a TRY merely because it appears nearby. The current runtime executes cleanup only when the operation is a direct child of TRY with Branch set to finally.

!
A FINALLY failure can replace the earlier outcome

A failing cleanup operation propagates its own error. Make cleanup idempotent, null-safe, and independently testable.

Real use case

Call a customer system and return a controlled result

TRY  (pair: try-catch-2)
├── Map pipeline: build customer request
├── Invoke customer service
└── Map pipeline: result.status = "SUCCESS"

CATCH  (pair: try-catch-2)
├── Logger: "Customer lookup failed"
└── Map pipeline
    errorDoc.errorMessage -> result.message
    errorDoc.stepName     -> result.failedStep
    "FAILED"             -> result.status

TRY child with Branch = finally
└── Logger: "Customer lookup attempt completed"

Map Service Output: result -> response

On success, CATCH is skipped. On failure, CATCH creates a stable result and the service continues. The final audit log runs on both paths.

Advanced behavior

Use nested handlers and EXIT deliberately

  • An inner TRY/CATCH can handle a local error and allow the outer flow to continue.
  • If an inner CATCH fails, an enclosing TRY/CATCH may handle that new error.
  • A normal EXIT with Exception false is control flow, so CATCH does not run; the associated FINALLY branch still runs.
  • EXIT with Exception true raises FLOW_EXIT_EXCEPTION and can be handled by CATCH.
  • Keep each TRY focused. Narrow scopes make the failing step and recovery intent easier to understand.

See Exit for Flow exit, Loop exit, exception mode, and their exact interaction with error handling.

Good practices

Make recovery predictable and observable

  • Keep the generated TRY and CATCH pair together at the same parent level.
  • Add Comments that explain what is protected, what is recovered, and what cleanup occurs.
  • Map a stable error contract in CATCH instead of exposing raw runtime details.
  • Copy required errorDoc values before CATCH finishes because the document is temporary.
  • Use FINALLY only for work that is safe to run after both success and failure.
  • Avoid logging passwords, tokens, private payloads, or full confidential request bodies.
  • Test TRY success, TRY failure, CATCH failure, FINALLY failure, normal EXIT, and exceptional EXIT separately.
