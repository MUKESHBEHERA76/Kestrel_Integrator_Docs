Project / Reusable Service / Loop

Run child steps once for every item in a list.

LOOP iterates a selected String List, Document List, Document Reference List, or Object List in order. During each iteration, child steps see the selected list path as the current single item and receive a zero-based loopIndex.

What LOOP does

Iterate list items sequentially

Use LOOP when the same mapping, utility, validation, or service call must run for every item in a list.

Input typeCurrent item type inside LOOPExample
String ListStringtags becomes one tag per iteration.
Document ListDocumentorders becomes one order document.
Document Reference ListDocument ReferenceThe referenced list becomes one typed document.
Object ListObjectThe list becomes one object per iteration.

Items execute in their original list order. LOOP completes one item's child steps before starting the next item.

Current item behavior

The selected list path becomes one item inside child steps

LOOP temporarily replaces the list value at its original pipeline path with the current item.

Outside LOOPInside a LOOP child
${pipeline.input.orders} is a Document List.${pipeline.input.orders} is the current Document.
A field normally requires an index: ${pipeline.input.orders[0].orderId}.Use the current item directly: ${pipeline.input.orders.orderId}.
${pipeline.input.tags} is a String List.${pipeline.input.tags} is the current String.
i
The original list is restored afterward

After normal completion, loop exit, or an error, Kestrel restores the original list at the selected path. Output values created by child steps remain available.

Steps inside LOOP

Build the work performed for each item

LOOP is a container. It does not expose its own pipeline mapper; select its child steps to configure data movement.

  1. 1
    Select LOOP

    Use its Add child action to create a Map pipeline child, or drag another Flow/Utils item inside it.

  2. 2
    Map the current item

    Child pipeline fields display the chosen list as the corresponding single-item type.

  3. 3
    Add processing steps

    Use mappings, utilities, project-service calls, IF-ELSE, SWITCH, TRY/CATCH, nested loops, or EXIT as required.

  4. 4
    Order the children

    Every child runs in tree order for the current item before the next iteration begins.

LOOP  (${pipeline.input.orders})
├── Map pipeline: prepare current order request
├── Project service: validateOrder
├── IF-ELSE: validation result
│   ├── IF valid: append result
│   └── ELSE: EXIT Loop or raise error
└── Logger: processed current order

Map pipeline: build final response

loopIndex

Know which item is currently executing

For each iteration, Kestrel writes the zero-based index as a String at ${pipeline.output.loopIndex}.

Iteration${pipeline.output.loopIndex}
First item"0"
Second item"1"
Third item"2"

Use loopIndex in messages, conditions, target-list index mapping, or correlation fields. When mapping the current item into a result Document List, set the target index to ${pipeline.output.loopIndex}.

!
loopIndex exists only in loop scope

After LOOP finishes, the previous loopIndex is restored. If there was no previous value, it is removed.

Stop iteration

Use EXIT to break out of LOOP

An EXIT child can stop only the current loop or stop the complete reusable service.

EXIT configurationBehavior
Exit from = Loop with matching Loop idStops remaining iterations and continues with the first step after LOOP.
Exit from = FlowStops the complete reusable service flow.
Exception = trueRaises an error using the configured, pipeline-substituted Error Message.

Give every loop a unique Id and enter that same value in the EXIT step's Loop id. Explicit IDs make nested-loop behavior clear and avoid relying on internal step identifiers.

Real use case

Validate and collect order results

A reusable service accepts a Document List of orders, validates each one, and builds an equally ordered result list.

Service input

{
  "orders": [
    { "orderId": "ORD-1", "amount": 125.00 },
    { "orderId": "ORD-2", "amount": 80.00 }
  ]
}

LOOP configuration

ItemValue
Input list${pipeline.input.orders}
Loop Idvalidate-orders
Current order ID inside child${pipeline.input.orders.orderId}
Current amount inside child${pipeline.input.orders.amount}
Result target index${pipeline.output.loopIndex}

Service output

{
  "results": [
    { "orderId": "ORD-1", "valid": true },
    { "orderId": "ORD-2", "valid": true }
  ]
}

The result mapping uses loopIndex as the target-list index, preserving the input order.

A child step failsThe original list and earlier loopIndex are restored, then the error follows normal service error handling.

Good practices

Keep iteration predictable

  • Add a Comment that states what the loop processes.
  • Assign a unique Loop Id, especially when loops are nested or EXIT is used.
  • Remember that the selected list path represents the current item inside children.
  • Use loopIndex when building an output list that must retain input order.
  • Keep side-effecting child calls idempotent when retries could repeat an item.
  • Use TRY/CATCH inside LOOP when one failed item should be handled without losing the intended service behavior.
  • Avoid logging complete current documents when they contain credentials or sensitive business data.
  • Test empty, one-item, multi-item, invalid-item, and early-exit scenarios.
