Project / KVS

Reusable project values, available at workflow runtime.

KVS means Key Value Store. It keeps related configuration under a named store, lets every key contain one or more ordered values, and gives workflows a consistent way to retrieve them without hard-coding values into each design.

KVS concept

Store once, resolve wherever the project needs it

A store groups related settings such as department codes, routing targets, feature switches, recipient lists, or credentials. Each key has at least one value and can hold multiple values when a workflow needs a list.

Create a store

How to add a KVS to a project

Administrators and developers can create and manage KVS stores. Choose password mode when the store is first created.

  1. 1
    Open the project

    Select the project that owns the configuration. The KVS will not be shared automatically with other projects.

  2. 2
    Open KVS and select Add KVS

    The KVS page lists the existing stores for the current project and identifies each as Plain or Password.

  3. 3
    Name and describe the store

    Use letters and underscores only—for example, employee_store or integration_secrets. The name must be unique inside the project.

  4. 4
    Choose Is Password

    Enable it for credentials or other values that must never be returned to the management UI/API. This choice is locked after creation.

  5. 5
    Add keys and values

    Every store needs at least one key, and every key needs at least one value. Add more value rows when that key represents an ordered list.

  6. 6
    Create the store

    Kestrel encrypts every value before saving it and refreshes the project metadata cache used by workflow lookups.

Is Password

Encryption is always on; visibility is the difference

The Is Password option does not decide whether Kestrel encrypts values. All KVS values are encrypted before PostgreSQL storage. It decides whether authorized management users can read the original value again.

!
A retrieved secret enters the workflow pipeline

Password mode protects management visibility and storage. After a workflow retrieves a secret, do not send it to Logger/Pipeline Logger or include it in snapshots. Use secret-like field names so baseline masking can recognize it, and map it only to the connector input that needs it.

Workflow utilities

Read KVS values with three utility operations

Use the store and key reference format kvsName.keyName. Pipeline substitution can provide these inputs dynamically.

UtilityInputOutputUse when
kvs:getValueemployee_store.employee_id{ "value": "12345" }You need the first value for one key.
kvs:getValuesemployee_store.roles{ "values": ["admin", "user", "viewer"] }You need every ordered value for one key.
kvs:getValuesList[employee_store.employee_id, employee_store.department]{ "values": ["12345", "finance"] }You need the first value from several keys in the same input order.
Default

throwErrorOnFailure = false

A missing or invalid reference returns an empty string or empty list, allowing the workflow to decide what happens next.

Strict

throwErrorOnFailure = true

An invalid reference, missing KVS, or missing key fails the step with UTILITY_ERROR. The option must resolve to literal true or false.

Runtime behavior

How a saved value reaches a running workflow

The database remains persistent storage. A bounded metadata cache reduces repeated reads, while decryption occurs inside the KVS lookup utility.

Project-scoped resolution

The worker injects the executing workflow's project ID. A store with the same name in another project is a different store.

Cache is not the source of truth

Kestrel can use its in-memory metadata cache or Redis. Cache misses fall back to PostgreSQL, and create/update/delete operations invalidate cached KVS metadata.

Ordered results

Keys and their values retain their configured order. getValuesList also preserves the order of the requested references.
