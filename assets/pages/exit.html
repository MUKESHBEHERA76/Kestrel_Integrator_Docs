Project / Reusable Service / Exit

Stop a service flow or leave a loop deliberately.

EXIT is a control-flow step. It can finish the complete reusable service, break out of a selected LOOP, or raise a pipeline-aware exception that follows TRY/CATCH and normal runtime error handling.

What EXIT does

End execution without adding another operation

Use EXIT when the service should not continue to the remaining sibling steps.

ModeConfigurationResult
Normal flow exitExit from = Flow, Exception = falseStops the reusable service successfully and keeps output values already created.
Normal loop exitExit from = Loop, matching Loop id, Exception = falseStops remaining iterations and continues after that LOOP.
Exceptional exitException = trueRaises FLOW_EXIT_EXCEPTION with the substituted Error Message.
i
Normal EXIT is control flow, not a failure

With Exception set to false, EXIT records an exit outcome and does not create a business error. Set Exception to true only when the caller or a CATCH block must receive a failure.

Add the flow step

Create EXIT from the reusable service Flow tab

  1. 1
    Decide what should stop

    Choose whether this business path should finish the complete service, break one loop, or raise an error.

  2. 2
    Select Flow

    Find EXIT in the reusable service step library.

  3. 3
    Place EXIT in the correct branch

    Add it inside IF, ELSE IF, ELSE, CASE, DEFAULT, LOOP, TRY, CATCH, or another process container where the decision occurs.

  4. 4
    Configure Properties

    Select Exit from, Loop id when needed, Exception, Comment, and Error Message.

  5. 5
    Test both paths

    Verify the path that reaches EXIT and the path that continues normally.

!
Exception takes precedence over Exit from

When Exception is true, EXIT raises FLOW_EXIT_EXCEPTION. It does not perform a normal Flow or Loop break, even if Exit from is set to Loop.

Exit from Flow

Finish the complete reusable service early

Set Exit from = Flow and Exception = false.

  • Remaining child and sibling steps are skipped.
  • Execution does not return to steps after the container that contains EXIT.
  • Pipeline values and Service Output values created before EXIT remain available to the caller.
  • The EXIT step is traced as EXIT rather than ERROR.
  • FINALLY cleanup associated with an enclosing TRY still runs before the flow exit completes.
IF  (${pipeline.input.orders} == $null)
├── Map pipeline: status = NO_ORDERS
└── EXIT
    Exit from: Flow
    Exception: false

LOOP: process orders
Map pipeline: status = COMPLETED

When orders is null, status remains NO_ORDERS and the LOOP and final MAP steps are skipped.

Exit from Loop

Break iteration and continue after LOOP

Set Exit from = Loop, provide the matching Loop id, and leave Exception false.

  1. 1
    Name LOOP

    Set a unique Id such as find-customer on the enclosing LOOP.

  2. 2
    Add EXIT inside that LOOP

    Usually EXIT is placed inside an IF or SWITCH branch that identifies the stopping condition.

  3. 3
    Select Loop as the target

    Enter the same value, find-customer, in EXIT's Loop id.

  4. 4
    Continue afterward

    When EXIT runs, remaining child steps and list items are skipped; the first step after LOOP executes.

!
The Loop id must identify an active enclosing loop

A wrong target that is not caught by an active loop eventually fails with FLOW_EXIT_ERROR. Configure explicit unique IDs instead of relying on internal step identifiers.

Exceptional exit

Raise a controlled service failure

Set Exception = true when the current condition is invalid and the caller must receive a failure.

BehaviorResult
Error typeFLOW_EXIT_EXCEPTION
Error messageResolved from the configured Error Message.
Remaining normal stepsSkipped unless the failure is handled and flow logic continues through a CATCH design.
CallerReceives the service failure when no enclosing TRY/CATCH handles it.
MonitoringRecords the step as an error with the runtime error details.
 
Comment: Reject requests without a customer id
Exit from: Flow
Exception: true
Error Message: Customer id is required for request ${pipeline.input.requestId}

Pipeline-aware Error Message

Include useful runtime context without exposing secrets

The Error Message supports embedded pipeline substitution.

Order ${pipeline.input.order.orderId} cannot be processed

Unsupported channel: ${pipeline.input.order.channel}

Validation failed at item ${pipeline.output.loopIndex}

See Pipeline Sub for paths, lists, documents, and copying variable syntax.

!
Do not include secrets in errors

Error messages can appear in execution history and logs. Never substitute passwords, bearer tokens, client secrets, private keys, or confidential payloads.

Interaction with TRY/CATCH/FINALLY

Normal exits and exception exits behave differently

EXIT behavior inside TRYCATCHFINALLY
Exception false, Exit from FlowDoes not run because this is not an IntegrationRuntimeException.Runs cleanup before the flow finishes.
Exception false, matching Exit from LoopDoes not run.Runs while the exit propagates to the target loop.
Exception trueRuns when a matching enclosing TRY/CATCH handles FLOW_EXIT_EXCEPTION.Runs after TRY/CATCH handling.

Use Exception true when the CATCH branch must build an error response or perform recovery. Use a normal exit for an expected early-completion path.

Practical examples

Choose the EXIT mode from business intent

Use caseConfigurationWhy
No data is a valid outcomeFlow, Exception falseReturn an empty or NO_DATA response without running unnecessary steps.
Stop searching after a matchLoop, matching Loop id, Exception falseBreak remaining iterations and use the found result afterward.
Required input is missingException true with contextual messageFail the caller or route the error through CATCH.
Unsupported SWITCH valueEXIT in DEFAULT, Exception trueReject an unknown operation or channel explicitly.
Validation branch decides to stop normallyMap final status, then Flow with Exception falsePreserve a deliberate business result without treating it as a technical error.

Good practices

Make early termination obvious

  • Add a Comment explaining the business reason for EXIT.
  • Map the intended final Service Output before a normal Flow exit.
  • Use explicit unique Loop IDs and match them exactly in EXIT.
  • Use Exception false for expected control flow and true for an actual failure.
  • Write actionable Error Messages with safe identifiers, not sensitive values.
  • Place cleanup in FINALLY when it must run for normal completion, exit, and error paths.
  • Test the non-exit path, normal Flow exit, Loop exit, exceptional exit, and TRY/CATCH behavior.
