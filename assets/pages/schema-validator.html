Validate XML or JSON with Schema Validator.

Schema Validator checks a mapped payload against an uploaded XSD or the request or response schema of a selected OpenAPI operation. It returns a status and a structured list of issues so the workflow can route valid and invalid messages.

Workflow design

Add and configure the connector

  1. 1
    Place Schema Validator

    In the workflow editor, drag Schema Validator from the Connector tab onto the canvas. Connect it after the step that produces the XML or JSON data.

  2. 2
    Choose validation type

    Double-click the connector and select XML with XSD or JSON with OpenAPI. Changing the type clears the previous uploaded schema and selection.

  3. 3
    Upload the schema

    Upload an XSD file for XML, or an OpenAPI 3.0/3.1 JSON or YAML file for JSON. The file must be 2 MB or smaller. The upload is inspected immediately; correct parsing or schema errors before saving.

  4. 4
    Select JSON details

    For JSON only, choose Request body or Response body, then an operation, response status when needed, and media type. See the JSON example.

  5. 5
    Map the input

    Open the connector's settings icon. Map a source field or constant into Step In inString. Save the mapping, resolve workflow warnings, and save the workflow.

  6. 6
    Route the result

    Read validationStatus and Error from Step Out. Use a condition on the status to choose the valid or invalid path.

XML validation

Validate an XML text value against an XSD

Select XML with XSD and upload a valid .xsd or .xml schema file. Example XSD:

<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="employee">
    <xs:complexType>
      <xs:sequence>
        <xs:element name="id" type="xs:string"/>
        <xs:element name="status" type="xs:string"/>
      </xs:sequence>
    </xs:complexType>
  </xs:element>
</xs:schema>

Map an XML string such as <employee><id>E-1042</id><status>Active</status></employee> to inString. XML input must be text; a document object is not accepted for XML validation. XSD validation reports line-numbered problems where available. External DTDs and external schema access are disabled.

JSON validation

Select a body schema from OpenAPI

Upload an OpenAPI 3.0 or 3.1 JSON/YAML file. The editor reads operations under paths and shows each supported HTTP method and path, such as POST /employees · createEmployee. Local #/... references are supported; external file or URL references are not.

For example, an OpenAPI POST /employees request schema can require id and email. Map {"id":"emp_10482","email":"alex@example.com"} as JSON text or a parsed JSON document to inString. The runtime accepts a JSON string, map, list, or JSON node; a parsed webhook body does not need to be converted using Java-style toString(). Only operations with a body schema for the chosen direction appear in the dropdown.

Step contract

Map one input and read two outputs

PathTypeMeaning
${pipeline.input.inString}String input fieldRequired mapping. Supply XML text or JSON text/structured JSON from the previous step.
${pipeline.output.validationStatus}String"true" when valid; "false" when invalid or validation cannot complete.
${pipeline.output.Error}DocumentContainer for validation messages.
${pipeline.output.Error.ErrorList}DocumentListOne document per issue; an empty list when valid.
${pipeline.output.Error.ErrorList.errorMessage}String per list itemActual schema, parse, or input error message.

The connector writes its own Step Out values. Map those outputs into later steps according to the workflow pipeline rules; do not create a direct Pipeline In to Pipeline Out mapping to mimic the validator result. Use a condition that compares the string validationStatus with "true" or "false".

Runtime examples

Inspect the structured result

A valid payload returns:

{
  "validationStatus": "true",
  "Error": { "ErrorList": [] }
}

An invalid payload can return more than one issue:

{
  "validationStatus": "false",
  "Error": {
    "ErrorList": [
      { "errorMessage": "Line 18: value is not allowed by the XSD enumeration." },
      { "errorMessage": "Line 18: the status element is invalid." }
    ]
  }
}

Read this as a document with a list, not as the Java map text {ErrorList=[...]}. If you need JSON for an HTTP response or log destination, serialize the Error document as JSON in that downstream step. The validator collects up to 100 messages per run.

Warnings and handling

Separate design warnings from validation results

The workflow warning panel requires a validation type, an uploaded file, and an inString mapping. JSON additionally requires Request or Response, an operation, a media type, and a response status for Response validation. Invalid uploads are reported while inspecting the file.

At runtime, invalid XML/JSON, an empty input, a missing schema, a bad OpenAPI selection, or an input over the 10 MB validation limit returns validationStatus = "false" with a message in ErrorList. This is a validation result, so route it with a workflow condition; it does not automatically enter the Exception Handler. Unexpected platform failures outside validation are handled by the normal workflow error path.
