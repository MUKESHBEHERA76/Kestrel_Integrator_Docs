Workflow triggers / SubWorkflow

Invoke one workflow from another.

A subworkflow is a workflow that another workflow invokes. Put SubWorkflow Trigger at the start of the callable workflow, define its input and output variables, then use Call SubWorkflow in a parent workflow to run it.

Purpose

Why create a subworkflow?

Several workflows often need the same business logic: validate a customer, normalize an address, enrich an order, or format a response. Build that logic once as a child workflow and call it from each parent. Its named input and output variables make the boundary clear to other developers.

SubWorkflow Trigger belongs in the child. It marks that workflow as callable. Call SubWorkflow belongs in the parent. It selects the child and maps data across the call. The child is still a normal workflow with processing steps; it is started by another workflow instead of an external HTTP request, incoming email, or schedule. Each workflow has one trigger, so do not add another trigger to the child.

A parent and its child must be in the same project. The call needs no separate connection or credential. Use a subworkflow when you want a reusable, named workflow operation; use an ordinary connector when you only need that connector's single action.

Child workflow

Create the workflow that will be invoked

  1. 1
    Create and name the child

    Open Projects → your project → Workflows and create a workflow, for example NormalizeCustomer. Give it a name that tells callers what it does.

  2. 2
    Add SubWorkflow Trigger

    Drag SubWorkflow Trigger from the workflow trigger palette onto the canvas. Connect it to the first processing step. Double-click the trigger to see its input and output counts; the variable editor is the Workflow I/O action in the editor header.

  3. 3
    Declare Workflow I/O

    Open Workflow I/O. On the Input tab add the values the child expects. On the Output tab add the results it will return. Select Apply.

  4. 4
    Build the logic

    Configure the child's steps to read its input variables and write its output variables. Declaring an output does not populate it; a step must produce the value.

  5. 5
    Save the workflow

    Save the child before selecting it in a parent. The parent selector shows saved callable workflows from the same project.

Workflow I/O

Define the contract between parent and child

The Input tab describes what the child receives; the Output tab describes what it returns. Each variable has a name and type. Names start with a letter and then use letters, digits, or underscores. Use Add child field on Document or DocumentList to model nested data. DocumentReference and DocumentReferenceList can point to a project Data Structure.

SideExampleChild pipeline pathDeveloper responsibility
InputcustomerId (String)${pipeline.input.customerId}Map a parent value into it; read it in a child step.
Inputcustomer (Document)${pipeline.input.customer}Map structured data when the child needs several related fields.
OutputnormalizedName (String)${pipeline.output.normalizedName}Write this value in the child; map or use it in the parent after the call.

Supported variable types are String, Boolean, Number, Integer, Float, Object, ObjectList, StringList, Document, DocumentList, DocumentReference, and DocumentReferenceList. Keep the contract focused. When you rename, remove, or change a variable, review each parent workflow's Call SubWorkflow mappings.

Parent workflow

Call the child and use its result

  1. 1
    Place Call SubWorkflow

    Open a parent workflow in the same project. Drag Call SubWorkflow from Connectors into its execution path. The parent keeps its own trigger, such as Webhook Trigger.

  2. 2
    Select the child

    Double-click Call SubWorkflow and choose the saved child. The selector lists workflows with SubWorkflow Trigger in this project and shows the selected signature counts.

  3. 3
    Map Step In

    Open the call connector's pipeline settings. Connect the parent values to the child inputs that its logic needs. For example, map the parent's ${pipeline.input.customerId} to child input customerId. A constant can be used where appropriate.

  4. 4
    Map Step Out

    Map the child's output into a parent pipeline path that later steps will read. For example, make normalizedName available to a following response or database step. Keep input and output mapping directions distinct.

  5. 5
    Save and exercise the call

    Save the parent and run a representative request. Inspect the call step, returned values, and any errors in the execution details.

A workflow without SubWorkflow Trigger cannot be selected as a child. A workflow in another project does not appear in the selector.

Worked example

Reuse customer name normalization

Child: NormalizeCustomer. Add SubWorkflow Trigger. In Workflow I/O declare Input fullName (String) and Output normalizedName (String). Add processing logic that trims extra spaces and writes the result to ${pipeline.output.normalizedName}.

Parent: CreateCustomer. Start it with an appropriate trigger. Add Call SubWorkflow, select NormalizeCustomer, and map the parent's incoming name to child input fullName. Map child output normalizedName to a parent pipeline field. Use that field in the next step.

Parent input:              fullName = "  Alex  Rivera  "
Call Step In:             fullName = "  Alex  Rivera  "
Child writes:             normalizedName = "Alex Rivera"
Call Step Out in parent:  normalizedName = "Alex Rivera"
Next parent step:         reads normalizedName

The names in this example are illustrative. The actual pipeline also contains other values; mappings decide which data crosses the call boundary. A declared output with no value written by child logic will not magically contain a result.

Runtime behavior

What happens when the parent reaches the call

Kestrel resolves the selected saved workflow in the parent's project and checks that it has SubWorkflow Trigger. It creates a nested pipeline from the parent pipeline, applies configured input mappings, and executes the child topology within the parent's execution run. When the child completes, Kestrel applies output mappings and declared outputs to the parent pipeline. The parent then continues with its next step.

The call is synchronous: the parent waits for the child to finish. If the child fails, the error propagates to the parent workflow, where an Exception Handler path can handle it. Direct self-calls are rejected. Avoid indirect call cycles between several workflows as well. Save and retest parent mappings whenever the child contract changes.

Troubleshooting

Diagnose common issues

SymptomWhat to check
Child does not appear in the dropdownConfirm it is saved, has SubWorkflow Trigger, and belongs to the same project. Refresh the parent editor if it was just created.
SUBWORKFLOW_NOT_FOUNDThe saved child ID or name cannot be resolved in this project. Reselect it in Call SubWorkflow.
SUBWORKFLOW_NOT_CALLABLEThe selected workflow no longer has SubWorkflow Trigger. Restore that trigger or choose another child.
SUBWORKFLOW_RECURSION_ERRORThe workflow calls itself directly. Move shared logic into a separate child.
Child input is emptyReview the parent's Step In mapping and the path the child reads. Declaring an input does not supply its runtime value.
Parent receives no resultCheck that child logic writes the declared output and that Step Out mapping places it where the next parent step reads it.
Child execution failsInspect the parent run's failed call and error details, then handle or propagate the error through the parent's Exception Handler path.
