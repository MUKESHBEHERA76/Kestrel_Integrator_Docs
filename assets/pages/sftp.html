Workflow / SFTP

Connect to an SFTP server and manage remote files.

Set up SFTP in three parts: trust the server, create a reusable project connection, and select that connection in a workflow SFTP step. The workflow exchanges structured documents named SFTP_Request and SFTP_Response.

Setup overview

Complete these four steps in order

You need the SFTP hostname, port, username, authentication details, and permitted remote directory.

  1. 1
    Verify the server key

    Get the server's SSH host public key and verify its fingerprint with the server administrator.

  2. 2
    Create a Known Hosts credential

    Store the verified host public key in Security → Security Credentials.

  3. 3
    Create an SFTP connection

    In the project's Connections tab, enter the endpoint and user authentication details, then test the connection.

  4. 4
    Configure the workflow step

    Add SFTP to a workflow, select the connection and operation, then map SFTP_Request and SFTP_Response.

!
Host key and login key are different

The server's host public key verifies the server and belongs in Known Hosts. A user's private key authenticates Kestrel to the server and belongs in the Keystore. Never put a private key in Known Hosts.

Step 1 and 2

Generate and store Known Hosts content

The examples use reserved placeholder values. Replace sftp.example.com and 22 with your server's real hostname and port.

1. Read the server host keys

ssh-keyscan -p 22 sftp.example.com

The command returns comments and one or more public-key entries:

# sftp.example.com:22 SSH-2.0-OpenSSH
sftp.example.com ssh-ed25519 <complete-base64-public-key>
sftp.example.com ecdsa-sha2-nistp256 <complete-base64-public-key>
sftp.example.com ssh-rsa <complete-base64-public-key>

Use the complete output from your command. Each key entry must stay on one line:

hostname key-algorithm complete-base64-public-key

2. Calculate the SHA-256 fingerprints

ssh-keyscan -p 22 sftp.example.com 2>/dev/null | ssh-keygen -lf - -E sha256
256 SHA256:<fingerprint> sftp.example.com (ED25519)
256 SHA256:<fingerprint> sftp.example.com (ECDSA)
3072 SHA256:<fingerprint> sftp.example.com (RSA)
!
Verify before trusting

ssh-keyscan reads the key but does not prove it is genuine. Compare the fingerprint with the SFTP administrator or provider through a separate trusted channel.

3. Save the credential in Kestrel

  1. 1
    Open Security Credentials

    Go to Security → Security Credentials and select Add security credential.

  2. 2
    Select the correct type

    Choose Known Hosts (SSH).

  3. 3
    Enter the values

    Use a neutral alias such as SFTP_PRODUCTION_KNOWN_HOSTS, add a description, and paste the complete key entries.

  4. 4
    Save

    The credential is now available in the SFTP connection editor. Refresh the Connections page if it was already open.

Alias name: SFTP_PRODUCTION_KNOWN_HOSTS
Credential Type: Known Hosts (SSH)
Description: Verified host keys for the production SFTP endpoint
Known Hosts content:
  sftp.example.com ssh-ed25519 <complete-base64-public-key>
  sftp.example.com ecdsa-sha2-nistp256 <complete-base64-public-key>

For a non-default port, OpenSSH normally produces a host token such as [sftp.example.com]:2222. Kestrel also supports hashed OpenSSH host entries.

Step 4

Add SFTP to a workflow

The workflow uses an active SFTP connection from the same project.

  1. 1
    Add the connector

    Drag SFTP from the connector palette onto the workflow canvas.

  2. 2
    Configure the step

    Double-click the step and select the project SFTP connection.

  3. 3
    Select an operation

    Choose the file or directory action to perform.

  4. 4
    Map the request

    Open Pipeline settings and map or hardcode fields under the SFTP_Request Document.

  5. 5
    Map the response

    Map values from the SFTP_Response Document to the next step or pipeline output.

  6. 6
    Save and run

    Save the mapping and workflow, then inspect the execution result.

!
Review mappings after changing an operation

Each operation has a different request and response structure. Changing the selected operation rebuilds the Step In and Step Out fields.

Document contract

Understand the request and response documents

Inputs are children of ${pipeline.input.SFTP_Request}. Results are written to ${pipeline.output.SFTP_Response}.

Fields returned by every successful operation

FieldTypeMeaning
successBooleantrue. Failures raise SFTP_EXECUTION_ERROR.
operationStringExecuted operation, such as LIST or UPLOAD.
pathStringResolved remote path.
timestampStringUTC ISO-8601 completion time.

Operation reference

Inputs, outputs, and purpose of every operation

Every response also includes success, operation, path, and timestamp.

Important Upload behavior

Upload first writes a temporary file named like <target>.kestrel-<unique-id>.part. After all bytes are written, the connector renames it to the requested target. This prevents another process from reading a partially uploaded file. The connector attempts to remove the temporary file if the upload fails.

i
Current design-time field visibility

The runtime Upload response contains size, and Move contains sourcePath and targetPath. These fields may not appear in the current Step Out tree, but they are present in the runtime SFTP_Response.

Mapping examples

Use relative paths inside the configured directory

These examples assume the Default remote directory is /data/inbound.

List the default directory

SFTP_Request:
  path: .

Upload a UTF-8 JSON document

SFTP_Request:
  path: orders.json
  content: ${pipeline.input.orderJson}
  contentEncoding: UTF8
  overwrite: false
  createParentDirectories: true

# Final path: /data/inbound/orders.json

Upload a Base64 file

SFTP_Request:
  path: documents/report.pdf
  content: ${pipeline.input.reportBase64}
  contentEncoding: BASE64
  overwrite: true
  createParentDirectories: true

Move a processed file

SFTP_Request:
  sourcePath: orders.json
  targetPath: archive/orders.json
  overwrite: false
  createParentDirectories: true
i
Prefer relative paths

For Default remote directory /data/inbound, the relative path orders.json resolves to /data/inbound/orders.json. Relative paths make workflows easier to move between environments.

Troubleshooting

Common SFTP setup and execution errors

Test the project connection first. If it succeeds, check the workflow connection selection and request mapping.

Error or symptomWhat to check
Server key did not validateUse the exact hostname and port. Ensure every Known Hosts entry is complete and on one line. Verify the current fingerprint with the server owner before updating it.
Known Hosts credential is not listedConfirm the credential type is Known Hosts (SSH), save it, and refresh or reopen the Connections page.
No more authentication methods availableCheck username, password, private-key alias, key passphrase, selected authentication type, and whether the matching public key is installed for the remote account.
SFTP connection is not listed in the workflowConfirm it is an active SFTP connection in the same project, then refresh or reopen the workflow editor.
Path is outside the Default DirectoryUse a relative path or an absolute path below the configured directory. Parent traversal with .. is not allowed.
File exceeds the inline limitIncrease Maximum inline file size within the allowed range or use a streaming design for larger files.
Rename or overwrite is rejectedThe server may not support the requested SFTP rename mode. Try a new target with overwrite disabled, or confirm overwrite/rename support with the server administrator.
Permission deniedConfirm the account has the required list, read, write, rename, or delete permission on the configured directory.
Delete directory failsThe directory must be empty and must not be the configured root.
!
Do not bypass a host-key failure

A changed host key can indicate a legitimate rotation or a security problem. Verify the new fingerprint through a trusted channel before changing the credential.
