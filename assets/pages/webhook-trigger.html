Workflow triggers / HTTP

Receive HTTP requests with Webhook Trigger.

Webhook Trigger starts an enabled workflow when an external client calls its endpoint. It places headers, query parameters, and the request body in the pipeline, including multipart files and binary content.

Design

Configure the entry point

  1. 1
    Add one trigger

    Open a workflow in Projects, drag Webhook Trigger from Workflow triggers, and connect it to the first executable step.

  2. 2
    Configure it

    Double-click the trigger. Set the resource name and HTTP method (POST by default), and declare expected headers or query parameters for the editor contract.

  3. 3
    Choose authentication

    Select None, Basic, API-Key, or JWT and provide the corresponding Webhook Auth alias if required. Configure aliases in Security → Webhook Auth.

  4. 4
    Map and enable

    Use the settings icon to inspect the pipeline. Map values needed by downstream steps, resolve warnings, save, and enable the workflow.

Call /api/triggers/projects/{projectId}/workflows/{workflowName}/{resourceName} with the configured HTTP method. The runtime also exposes /api/triggers/webhook/{artifactId}. Use URL encoding for dynamic path segments.

Access control

Authenticate external callers

ModeRequest requirement
NoneNo webhook credential. Use only when this exposure is intended.
BasicAuthorization: Basic … matching the selected Basic alias.
API-KeyConfigured API key in the configured header name.
JWTAuthorization: Bearer … validated against the selected JWT alias.

An Administrator creates or changes aliases; a Developer or Administrator can select an alias on the trigger. See the Webhook Auth guide for setup, credential rotation, and JWT verification details.

Authentication failures return HTTP 401. Sensitive authorization, cookie, API-key, and idempotency headers are redacted in the pipeline header copy.

Content types

Receive text, documents, forms, and files

Request bodyPipeline body shape
JSONParsed object or array when valid. A top-level object containing file objects with fileName and contentBase64 produces a file-record array in body; the original object is available in bodyByField. Other JSON bodies retain their shape.
Text or XMLString. JSON-looking text may also be parsed as JSON.
application/x-www-form-urlencodedDocument of form keys and values; repeated keys become lists.
multipart/form-data with filesbody is an array of file records, regardless of submitted field names. Text fields are in formFields; the original keyed representation is in bodyByField.
multipart/form-data without filesDocument of submitted text fields.
Binary media, such as image or PDFDocument with contentType, size, and contentBase64.

Each file record contains fieldName, fileName, contentType, size, and contentBase64 when provided. fieldName is the form key or JSON property name; fileName is the uploaded filename. Decode Base64 downstream when binary bytes are needed. The request-body limit defaults to 1,048,576 bytes; requests over the configured limit are rejected with HTTP 413.

Output contract

Map the incoming request

Pipeline pathRuntime typeMeaning
${pipeline.input.webHookRequest.body}Dynamic; Document List when files are presentArray of file records for multipart uploads or top-level JSON file objects; otherwise the ordinary request body.
${pipeline.input.webHookRequest.attachments}Document ListTyped alias of the file-record array; empty when no files are present.
${pipeline.input.webHookRequest.attachments.fieldName}StringSubmitted form key or JSON property name, such as 1 or billingfile.
${pipeline.input.webHookRequest.attachments.fileName}, contentType, size, contentBase64String, String, Number, StringFilename, MIME type, byte size, and Base64 payload of each file.
${pipeline.input.webHookRequest.formFields}DocumentMultipart text fields; repeated names become lists.
${pipeline.input.webHookRequest.bodyByField}DocumentOriginal keyed body when files are present. Use for older mappings that accessed body.billingfile.
${pipeline.input.webHookRequest.headers}DocumentRequest headers with sensitive values redacted.
${pipeline.input.webHookRequest.queryparam}DocumentDecoded URL query parameters; repeated keys become lists.
${pipeline.input.body}DynamicTop-level alias of webHookRequest.body.
${pipeline.input.triggerType}Stringwebhook.

Map attachments as a Document List or iterate the array in body. Each record carries its own names, so no file key or filename has to be declared at design time. File-bearing requests now use the array body; update older mappings from body.billingfile to bodyByField.billingfile if keyed access is still needed. The log viewer may omit large Base64 text for display while the runtime payload retains it.

Example

Upload two files and a text field

curl -X POST 'http://localhost:8080/api/triggers/projects/PROJECT_ID/workflows/Orders/upload' \
  -F 'caseId=C-1042' -F '1=@invoice.pdf' -F '2=@photo.jpg'

The pipeline receives the following shape. Base64 data is shortened for readability.

{
  "webHookRequest": {
    "body": [
      {"fieldName":"1","fileName":"invoice.pdf","contentType":"application/pdf","size":1234,"contentBase64":"..."},
      {"fieldName":"2","fileName":"photo.jpg","contentType":"image/jpeg","size":5678,"contentBase64":"..."}
    ],
    "attachments": [
      {"fieldName":"1","fileName":"invoice.pdf","contentType":"application/pdf","size":1234,"contentBase64":"..."},
      {"fieldName":"2","fileName":"photo.jpg","contentType":"image/jpeg","size":5678,"contentBase64":"..."}
    ],
    "formFields": {"caseId":"C-1042"},
    "bodyByField": {
      "caseId":"C-1042",
      "1":{"fileName":"invoice.pdf","contentType":"application/pdf","size":1234,"contentBase64":"..."},
      "2":{"fileName":"photo.jpg","contentType":"image/jpeg","size":5678,"contentBase64":"..."}
    }
  }
}

Postman form-data keys may have any names. fieldName preserves each key inside the array item. The attachments path offers the same records as a typed Document List for mapping. The client sets the multipart boundary automatically.

Execution response

Handle completed and accepted runs

If the run has completed, the endpoint returns the workflow response, using pipeline output responseCode, responseHeaders, and response or responseBody when configured. If execution is still active, HTTP 202 includes runId, status, execution state, a Location header pointing to /api/triggers/runs/{runId}, and Retry-After: 2. Poll that URL to obtain the final response.

A wrong method returns 405; disabled workflows return 423; failed executions return an error response. An optional Idempotency-Key header can identify retries of the same request.
