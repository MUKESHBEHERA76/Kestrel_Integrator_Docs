Workflow concept

One project-owned integration flow

A workflow belongs to a project and combines a trigger, connected steps, pipeline mappings, branching rules, and error handling into one versioned design.

At runtime, Kestrel executes the saved workflow topology from its trigger through the connected arrows. Each step reads its mapped inputs, performs one operation, and writes outputs that later steps can use. A workflow can call external systems through connectors, transform values through utilities, invoke project services, return an HTTP response, log useful information, and finish explicitly.

i
A workflow is different from a reusable service

A workflow owns an execution entry point. A reusable service packages shared logic that another flow calls and does not require its own external trigger.

Workflow Trigger

The trigger defines how execution begins

Every workflow requires one trigger, and only one trigger is allowed. Add it first; Connectors and Utils unlock after a trigger exists.

TriggerUse it whenKey configuration
Webhook TriggerAn external client must start the workflow through HTTP.Resource name, HTTP method, expected query parameters and headers, plus optional Basic or API-key authentication alias. The incoming request becomes available to the workflow pipeline.
Scheduler TriggerThe workflow must run on a time-based schedule.Cron schedule and scheduler state. The workflow must be enabled before its scheduler can be enabled.
SubWorkflow TriggerAnother workflow must invoke this workflow as a reusable child flow.Workflow input and output signature. The editor exposes a Workflow I/O action for defining the contract.
!
The trigger is the first topology step

Connect the trigger to the first executable step. If you need a different trigger type, remove the existing trigger before adding another one.

How to use a utility

  1. 1
    Open Utils

    Add and configure the workflow trigger first, then select the Utils tab in the palette.

  2. 2
    Find the utility

    Use the palette search or browse the grouped utility names.

  3. 3
    Drag it onto the canvas

    Place the utility in the required execution order and connect the previous step to it.

  4. 4
    Map Step In

    Open pipeline settings and map the source pipeline values to the utility's required input fields.

  5. 5
    Map Step Out

    Map the utility result to Pipeline Out so later steps can consume it, then connect the next arrow.

Overall workflow

A practical build sequence

Following the same order makes the editor easier to understand and reduces validation issues.

  1. 1
    Add and configure one trigger

    Choose Webhook, Scheduler, or SubWorkflow based on who starts the execution.

  2. 2
    Add an Exception Handler

    Every workflow requires one exception handler with a connected recovery path.

  3. 3
    Add connectors, utilities, services, and actions

    Drag only the steps needed for the integration and keep each step focused.

  4. 4
    Connect the topology

    Draw arrows in execution order. Add conditions only where the flow branches.

  5. 5
    Configure every step

    Double-click each node and provide its required design-time options.

  6. 6
    Map data

    Open pipeline settings for each step and map Step In and Step Out deliberately.

  7. 7
    Add the intended outcome

    Use Send HttpResponse for request-driven responses and Workflow End for an explicit terminal step where appropriate.

  8. 8
    Review issues and save

    Correct missing trigger, exception handling, connector configuration, and other reported problems before execution.

Save and execution

Validate the design before running it

Save persists a new workflow definition version after validation. Run eligibility depends on the trigger type.

  • Save — review the issues indicator first, then save the configured topology and mappings.
  • Run — manual editor execution is available for eligible trigger types such as Scheduler and SubWorkflow.
  • Webhook — invoke the generated trigger URL using its configured HTTP method instead of the editor Run button.
  • Scheduler — enable the workflow before enabling its scheduler.
  • Enabled state — disabling a workflow prevents scheduled execution without deleting its design.
  • Monitoring — use Monitor → Local Analytics for PostgreSQL-backed execution history and OpenSearch Analytics when external log search is configured.
