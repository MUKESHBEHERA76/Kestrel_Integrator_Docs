Understand the pipeline envelope

The examples in the tables show the contents of Salesforce_Request and the meaningful part of Salesforce_Response.body. Map the request fields in Step In. Map Salesforce_Response from Step Out to Pipeline Out before another step reads it. The connector always writes statusCode (Number), contentType (String), headers (Document), and body (parsed JSON Document/List or raw XML/CSV String). REST record actions also expose recordId.

Step In:  Salesforce_Request = {"body":{"Name":"Acme"}}
Step Out: Salesforce_Response = {
  "statusCode": 201,
  "contentType": "application/json",
  "headers": {"content-type":"application/json"},
  "body": {"id":"001000000000001AAA","success":true,"errors":[]},
  "recordId": "001000000000001AAA"
}

Responses below are illustrative success examples. Salesforce can add fields, return a different successful status, or return an empty body. A failed Salesforce call throws a workflow error and is handled by the workflow Exception Handler; it does not produce a successful Salesforce_Response. For Bulk 1.0 XML responses, body is XML text, so parse it or request JSON before mapping a nested body.id. A webhook's own HTTP 200 does not prove the Salesforce step succeeded.

API type: REST

Record and SOQL actions

Set Object API name to Account for record actions. Query SOQL does not use an object name. Use the record ID assigned by Salesforce; it is separate from body.

Get record · GET{"recordId":"001000000000001AAA"}statusCode: 200; body: {"Id":"001000000000001AAA","Name":"Acme"}; recordId echoes the input.
Update record · PATCH{"recordId":"001000000000001AAA","body":{"Phone":"+14155550199"}}statusCode: 204; body: ""; recordId echoes the input. Map changed fields only; do not include Id in the body.

API type: Apex Call

GET, POST, PUT, PATCH, and DELETE

Set a default Apex REST path such as orders, or map the optional Salesforce_Request.path for each run. Kestrel prefixes /services/apexrest/. Every method can map queryParamList and headerList; these are DocumentLists of {"name":"...","value":"..."} and {"headerName":"...","headerValue":"..."}. Their values are optional. The Apex class defines the actual request and response schema, so the response bodies below are an example for a custom orders class, not a Salesforce standard contract.

Shared optional queryParamList: [{"name":"include","value":"lines"}]
Shared optional headerList: [{"headerName":"X-Correlation-Id","headerValue":"run-1001"}]

POST{"path":"orders","body":{"orderId":"SO-1002","status":"Open"}}statusCode: 201; body: {"orderId":"SO-1002"}.

Custom header and query lists may be mapped alongside any row. Kestrel supplies authentication; do not map an Authorization header. The Apex endpoint may use other status codes or return XML/plain text if your class defines them.

API type: Event Processing

Publish a platform event

Choose Publish platform event and configure the event API name, for example Demo_Notification__e. Map Salesforce_Request.body = {"Message__c":"Order SO-1002 is ready"}. Kestrel POSTs to the event sObject endpoint. An illustrative success is Salesforce_Response.statusCode = 201 and body = {"id":"e00...","success":true,"errors":[]}. The event ID is in body.id; Kestrel's dedicated recordId output is for REST record actions. Publishing does not mean a separate Salesforce Trigger has consumed the event.

API type: REST Bulk

Bulk API 1.0 jobs and batches

Each row is one Salesforce step. The job ID returned by Create job starts with 750; a Salesforce user ID beginning 005 is not a job ID. A batch ID is a separate ID returned by Add batch. Configure Request content type on Create job and Add batch independently. The job definition's contentType determines whether later batches are CSV, JSON, or XML; it is different from the HTTP header used to send the job definition. See Bulk format configuration.

Create job Step In (Request content type: JSON):
{"body":{"operation":"insert","object":"Account","contentType":"JSON"}}

Add batch Step In (Request content type: JSON):
{"jobId":"750000000000001AAA","body":[
  {"Name":"Bulk Account Alpha","Phone":"+15550111"},
  {"Name":"Bulk Account Beta","Phone":"+15550122"}
]}

A plain JSON array of Account records is a valid Bulk API 1.0 JSON batch. The job must have been created for Account with contentType: JSON. If the job uses CSV, map CSV text such as Name,Phone Bulk Account Alpha,+15550111 and select CSV on Add batch. Salesforce's batch format guide describes record file formats.

Abort job · POST{"jobId":"750000000000001AAA"}Kestrel generates state Aborted. Example response: body: {"id":"750000000000001AAA","state":"Aborted"}. Aborting does not undo already processed records.

Bulk API 1.0 result bodies depend on the job content type and Salesforce's response headers. Kestrel parses JSON responses, but leaves XML and CSV as strings. Use Salesforce_Response.contentType rather than assuming that all responses are JSON. Salesforce documents per-record result retrieval in its Retrieve Batch Results guide.

API type: REST Bulk 2.0

Ingest and query jobs

Job configuration and state changes use JSON. Upload data uses CSV text. Bulk API 2.0 ingest accepts contentType: CSV in the Create ingest job body; contentType: JSON is rejected. The query job is a separate job type and needs no Upload CSV step. Read a successful Create job response's body.id for later Salesforce_Request.jobId. The exact status and processing time vary.

Action / HTTPSalesforce_Request exampleSuccessful Salesforce_Response example
Create ingest job · POST{"body":{"object":"Account","operation":"insert","contentType":"CSV","lineEnding":"LF"}}body: {"id":"750000000000001AAA","state":"Open","object":"Account","operation":"insert","contentType":"CSV"}. Save body.id.
Upload CSV · PUT{"jobId":"750000000000001AAA","body":"Name,Phone\nBulk Account Alpha,+15550111\nBulk Account Beta,+15550122"}statusCode: 201; body: "" is typical. This means Salesforce received CSV, not that all records processed successfully.
Close job · PATCH{"jobId":"750000000000001AAA"}Kestrel sends {"state":"UploadComplete"}. Example response: body: {"id":"750000000000001AAA","state":"UploadComplete"}.
Abort job · PATCH{"jobId":"750000000000001AAA"}Kestrel sends {"state":"Aborted"}. Example response: body: {"id":"750000000000001AAA","state":"Aborted"}.
Get job · GET{"jobId":"750000000000001AAA"}body: {"id":"750000000000001AAA","state":"JobComplete","numberRecordsProcessed":2,"numberRecordsFailed":0}. Poll until a terminal state before reading results.
Get failed results · GET{"jobId":"750000000000001AAA"}body is CSV text with failed records and error columns, or an empty CSV result when no records failed. Example: sf__Error,Name INVALID_FIELD,Bad Account.
Get successful results · GET{"jobId":"750000000000001AAA"}body is CSV text with successful rows, for example sf__Id,sf__Created,Name 001000000000001AAA,true,Bulk Account Alpha.
Get unprocessed results · GET{"jobId":"750000000000001AAA"}body is CSV text listing rows that Salesforce did not process; it may be empty.
Create query job · POST{"body":{"operation":"query","query":"SELECT Id, Name FROM Account LIMIT 100","contentType":"CSV"}}body: {"id":"750000000000002AAA","state":"UploadComplete","operation":"query"}. No record upload is needed.
Get query job · GET{"jobId":"750000000000002AAA"}body: {"id":"750000000000002AAA","state":"JobComplete","numberRecordsProcessed":1}. Wait for JobComplete before Get query results.
Get query results · GET{"jobId":"750000000000002AAA"}body is CSV text, for example Id,Name 001000000000001AAA,Acme. Inspect response headers for result pagination; the connector currently makes one results call.
Abort query job · PATCH{"jobId":"750000000000002AAA"}Kestrel sends {"state":"Aborted"}; an illustrative response has body.state: "Aborted".

Get failed/successful/unprocessed results and Get query results return raw CSV in Salesforce_Response.body, even though other Bulk 2.0 actions return parsed JSON. Salesforce's Upload Job Data and query job walkthrough describe these stages.

API type: REST Place Order

Commerce actions

These actions use Salesforce's commerce sale resources. Your org must support the resources, and its enabled features determine the accepted body schema. The request examples below identify the exact Kestrel pipeline fields; bodies marked illustrative must be replaced by the commerce payload required by your org. Read the actual Salesforce_Response.body and statusCode; Kestrel does not reshape the commerce response.

Action / HTTPSalesforce_Request exampleSalesforce_Response example / interpretation

Account: add orders · POST{"body":{"accountId":"001000000000001AAA","orders":[{"...":"org order fields"}]}} (illustrative)statusCode: 201; body contains Salesforce's order creation result.

End-to-end mapping

Pass real IDs between Salesforce steps

  1. 1
    Create a Bulk job

    For Bulk API 1.0, choose JSON and map {"operation":"insert","object":"Account","contentType":"JSON"} to Salesforce_Request.body. Select JSON response format if you need direct body.id mapping.

  2. 2
    Save the returned job ID

    Map Salesforce_Response.body.id from the Create job step to a runtime variable such as bulkJobId. Confirm that it begins with 750. A 005 user ID or 001 Account ID will fail Add batch.

  3. 3
    Upload and close

    Map the runtime value to Add batch Salesforce_Request.jobId; map the JSON record array to body and select JSON request content type. Save the returned batch ID. Close the same job after uploads.

  4. 4
    Check completion

    Get job and Get batch until processing completes, then Get batch results. Check record failures even when Add batch initially returned a successful HTTP status.

For Bulk API 2.0, use a CSV ingest job: Create ingest job → map body.id → Upload CSV → Close job (UploadComplete) → Get job → Get successful/failed/unprocessed results. For any action, review the workflow's Exception Handler when Salesforce returns a non-2xx response. See the Salesforce connector failure section.
