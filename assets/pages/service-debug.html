Inspect a reusable service one executed step at a time.

The full-page debugger shows the ordered flow, actual runtime variables, and the selected step's read-only pipeline. Use it to find where a value was created, changed, dropped, or sent to a utility.

Start a debug session

Open Debug from the reusable service editor

Debug runs the service with test input and opens a separate, full-page inspection view.

  1. 1
    Open a service

    Go to Projects → your project → Reusable services, and open the service you want to inspect.

  2. 2
    Click Debug

    The editor saves current changes first when it is editable. If saving fails, fix that error before starting a session.

  3. 3
    Provide test input

    Enter a JSON object matching Service I/O input, then start the session. For example, {"case":"priority"} supplies ${pipeline.input.case}.

  4. 4
    Inspect the first pause

    The service starts executing and pauses after it records a step. The selected flow-tree item, runtime variables, and pipeline view show that completed step.

i
Run and Debug have different purposes

Run executes the service and shows its final result. Debug creates a controllable run with per-step pipeline snapshots. A debug run executes real service logic, so use suitable test inputs when a utility or called service can change external data.

The debugger records snapshots before and after each traced step. A highlighted step has already run: its Runtime variables pane shows the after state. Selecting an earlier executed step lets you review history without changing execution or rolling values back.

Execution controls

Choose how far the service continues

Step in and Step out are available while the session is paused. Controls are disabled while a command is in progress or once the run has finished.

ControlBehaviorExample
Step inResume execution until the next step is recorded, then pause again.After a MAP step, Step in executes the following JSON utility and shows its output. It advances between service steps; it does not open the utility's internal code.
Step outResume through steps at the current nesting depth and deeper, then pause on the next step at a shallower depth.From a step inside a SWITCH case, continue through that case and pause after a step outside the case. From a top-level step, there may be no shallower step, so execution can finish.
RunResume without further per-step pauses until the service finishes or fails.Use after checking the suspicious mapping when you want the final service result.
TerminateRequest termination of the active debug run.Stop a test that should not continue. A step or external call already completed is not undone.
CloseClose the debugger. If the run is still active, the debugger first requests termination.Return to the service editor after inspecting a completed run.
!
The pause happens after a step

When you see PAUSED, the highlighted step has completed and its output is available. Step in allows the next step to run and then pauses after that step is recorded. A branch that is not taken has no executed trace to select.

Inspect data

See complete values without editing the pipeline

  • Variable icons use the same visual language as the reusable service pipeline. A text field, document, and list can be recognized by their icons; nested documents and lists can be expanded on demand.
  • Long values are shortened in the row so the panel stays readable. Double-click the variable name to open the read-only value viewer. It displays the full text; JSON text can be switched between formatted and raw views. Press Escape or Close to return.
  • Before/after values belong to the selected step. The Pipeline In side represents data before execution; Pipeline Out and Runtime variables represent data after execution.
  • Mapping lines show configured data movement for mapper and service-like steps. This is an inspection view: edit a mapping in the reusable service editor, save it, and start a new debug run to test the change.
  • System contains run metadata such as run ID, trigger, and current step. Other variables appear as they acquire values during execution.

If a field appears in the editor's schema but has no runtime value, inspect the source mapping and the preceding step. The runtime panel reflects actual captured values, while a mapping target can exist in the design before receiving data.

Worked example

Find where a JSON output was produced

Suppose a service builds a document list and calls json:documentListToJSON.

Test input and intended flow

{
  "employees": [
    { "employeeId": "EMP-1001", "name": "John Doe", "active": true },
    { "employeeId": "EMP-1002", "name": "Sarah Connor", "active": false }
  ]
}
  1. 1
    Map pipeline

    Map ${pipeline.input.employees} to the document list used by the JSON utility. At this pause, expand the list under Runtime variables and confirm both employees exist.

  2. 2
    Step in

    The utility executes. Select its trace and confirm that documentList is mapped on Service In and jsonString is mapped to ${pipeline.output.outputJson} on Service Out.

  3. 3
    Inspect outputJson

    The row may shorten the generated string. Double-click outputJson in Runtime variables to read the complete JSON array in the value viewer.

[
  { "employeeId": "EMP-1001", "name": "John Doe", "active": true },
  { "employeeId": "EMP-1002", "name": "Sarah Connor", "active": false }
]

If outputJson is absent, compare the utility's Service Out mapping with the preceding MAP step. If the list exists but contains the wrong fields, inspect the MAP step's after snapshot to find the first incorrect value.

Troubleshooting

Use the last recorded step and error details

What you seeWhat to check
FAILURE with an execution errorRead the error in the runtime pane, select the last executed step, and compare its Pipeline In with the values expected by that step. A failure can occur before a new successful trace is recorded.
Expected branch stays WAITINGInspect the executed IF/SWITCH condition and the input value. Unchosen branches are not executed and have no runtime snapshot.
A variable is missing after a stepInspect the prior executed step, its target path, any Drop operation, and the selected step's before/after snapshots.
Step out does not pause inside the current groupThat is expected: Step out skips pauses at the current nesting depth and deeper. Use Step in when every next step must be inspected.
No detailed value is visible in the rowExpand its parent document or list, then double-click the variable name to see its full value.

Session behavior

Plan debug sessions as temporary test runs

  • Debugging is available for reusable services to users with Developer or Administrator access.
  • The debugger keeps a bounded in-memory session and step history. An idle paused session is terminated after approximately 30 minutes; the platform also limits concurrent sessions and captured traces.
  • Trace selection is read-only. Clicking an earlier step changes what you inspect, not where the running service will resume.
  • Snapshots are captured for debug execution. They can contain test payloads and values returned by called services, so use suitable data when sharing screens or reports.
  • Workflow debugging follows its own execution path; this guide describes the full-page reusable service debugger.

For the service design itself, return to Reusable Service. For expression syntax and variable mapping, see Pipeline Sub and Map Pipeline.
