Monitor / Local Analytics

Find and inspect a workflow or service execution

Open /monitor/analytics. Choose Workflow Executions or Reusable Service Executions. The page loads saved execution runs, shows summary cards and activity charts for the filtered set, and presents one card per run. The current default date range is Past 24 Hours; you can select shorter ranges, 7 or 30 days, or a custom From/To interval.

Use the run ID to correlate a Local Analytics card with the same transaction in OpenSearch Analytics. Local Analytics is based on PostgreSQL execution records; it is not a live tail of the server console.

Custom-field search

Find a run by a Logger field

Custom fields come from the workflow Logger connector. Each row has a field name and value. The search is case-insensitive and supports * wildcards in either box. Multiple rows must all match the same run. An empty row is ignored.

  1. Configure a Logger on the executed workflow path with customFields=[{"name":"OrderNo","value":"${pipeline.input.webHookRequest.queryparam.orderno}"}].
  2. Run the workflow with ?orderno=123. The run stores OrderNo=123.
  3. Choose a date range containing the run. Enter field OrderNo and value 123; select Search in the Custom fields panel (or Apply above it).
  4. For an incomplete identifier, search OrderNo with *23*. Add a second row such as PoNo=567 to narrow the result.
  5. Open the run card: the custom fields appear separately from the Logger message. The log line can be a fixed message while the metadata values vary per run.
i
Date and retention matter

A correct field search returns no result when the run lies outside the selected date range or has been removed by PostgreSQL retention. Widen the range before changing your workflow mapping.

Monitor / Active threads

See work in progress

Open /monitor/threads to view current active workflow executions. The page shows each artifact and project, run ID, status, current step, start time, thread name, and thread state. Search by workflow name, project, current step, or run ID; use Refresh for a current snapshot.

When authorized, Terminate execution requests that the active run stop. The card changes to an abort-requested state while the runtime applies the request. A completed run is investigated in Local Analytics, not the Active threads list. Termination is not an undo for an external API call or database side effect that has already completed.

Example investigation
1. Search Active threads for run ID 63a9... or workflow OrderIngest.
2. Note the current step and how long it has been running.
3. Open Runtime Operations if queues, workers, or dependencies look unhealthy.
4. After completion, inspect the run in Local Analytics.

For worker-level Pause, Drain, and Resume, see Administration → Runtime Operations. Those controls are separate from terminating one execution.

Monitor / Configuration

Set PostgreSQL data retention

Open /monitor/configuration. The page manages two independent PostgreSQL policies. An administrator can select Edit configuration, choose days, confirm, and save. Other roles can inspect the values.

PolicyStorage and visible effectAllowed values
Runtime logsRemoves expired rows from ki_runtime_logs.1, 3, 7, 15, 30, 60, or 90 days
Completed execution runsRemoves expired terminal records from ki_execution_runs; removed runs no longer appear in Local Analytics.1, 3, 7, 15, 30, 60, or 90 days

Saving starts cleanup immediately; automatic cleanup continues hourly using UTC instants. Queued, accepted, claimed, running, and cancellation-requested runs are excluded. The page shows the last cleanup time and counts removed. Example: retain runtime logs for 7 days and completed runs for 90 days. This does not set OpenSearch index retention; configure that under OpenSearch → Configuration.

Developer reference

How Monitor retrieves its data

The frontend calls authenticated Kestrel endpoints. Recent runs use GET /api/execution/runs; a custom-field search uses POST /api/execution/runs/search. Opening a run loads its step logs from GET /api/observability/runs/{runId}/logs. Active threads use GET /api/execution/threads; termination uses POST /api/execution/threads/{runId}/terminate. Monitor Configuration uses GET and administrator-only PUT /api/observability/retention.

POST /api/execution/runs/search
Content-Type: application/json

{
  "customFields": [
    {"name": "OrderNo", "value": "*123*"},
    {"name": "PoNo", "value": "567"}
  ],
  "fromTime": "2026-10-18T00:00:00Z",
  "toTime": "2026-10-19T00:00:00Z"
}

The response is a list of execution runs; each matching run includes customFields such as {"OrderNo":"123","PoNo":"567"}. This request requires one to ten complete name/value filters and a valid date range. The application applies the run-type, status, and text controls to the returned runs.
