Logger connector

Write a message at a chosen severity and attach searchable name/value fields to the execution run. Logger does not need a connection and does not replace the workflow pipeline.

Step by step

Add Logger to a workflow

  1. Open Projects → your project → Workflows, open a workflow, and place Logger on the path whose executions you want to record. A Logger on an exception branch runs only when that branch executes.
  2. Open the Logger configuration and select DEBUG, INFO, WARN, or ERROR. Use INFO for ordinary business milestones and ERROR for a failure you handle in the workflow.
  3. Open Pipeline settings for that Logger. Map or hardcode logMessage and, when needed, add customFields. Save the mapping, then save the workflow.
  4. Run the workflow and inspect its run ID under Monitor → Local Analytics. Use the same run ID to correlate the transaction in OpenSearch → Analytics.

The selected level controls the log entry's severity; it does not change the workflow's success or failure status. A successful workflow can contain an ERROR level Logger entry.

Pipeline contract

Map the two Step In inputs

Step In fieldTypePurpose and example
logMessageStringMessage recorded for this step. Map a source, for example ${pipeline.input.webHookRequest.body}, or enter text such as Order ${pipeline.input.webHookRequest.queryparam.orderno} received. Pipeline expressions in configured text are resolved at runtime.
customFieldsDocumentList of name and value stringsOptional metadata added to the run. Example pairs: OrderNo=123 and PoNo=567. Use the root list's hardcode editor to enter multiple pairs, or map a compatible list from an earlier step.

To set a message from a source field, connect that source to logMessage in the pipeline editor. To use text with substitutions, open the field's hardcode editor and enter the whole string. A hardcoded value on the field takes precedence over a source mapping; remove or replace the hardcode if you want the source mapping to win. The Logger's configured message is a fallback when no Step In message resolves.

For custom fields, each name must begin with a letter and use letters, digits, underscore, hyphen, or period (at most 64 characters). A value may contain pipeline substitutions and is limited to 512 characters after resolution. A run can hold at most 20 custom fields. Reusing a name on a later Logger step updates that run's value.

Worked example

Webhook order with two search keys

Suppose a Webhook Trigger receives POST /orders?orderno=123&pono=567. Place Logger directly after the trigger and configure level INFO. In Pipeline settings, use these Step In values:

logMessage = Order ${pipeline.input.webHookRequest.queryparam.orderno} received

customFields = [
  {"name":"OrderNo","value":"${pipeline.input.webHookRequest.queryparam.orderno}"},
  {"name":"PoNo","value":"${pipeline.input.webHookRequest.queryparam.pono}"}
]

The runtime message is Order 123 received. The saved execution has {"OrderNo":"123","PoNo":"567"}. To enter the list, open the hardcode value for the customFields root, paste the JSON array, and save. The two child fields illustrate one pair; use the root list for multiple pairs.

i
Prefer identifiers over whole payloads

Use a purchase-order ID, correlation ID, or external reference as a custom field. Avoid passwords, tokens, full request bodies, and private customer data in messages or fields.

Runtime behavior

What Logger writes

Logger adds an entry with timestamp, level, step, and resolved message to the execution's logs. Its custom fields are stored on the execution run and published as transaction metadata for OpenSearch. The step has no business-payload Step Out fields, and the incoming pipeline remains available to following steps.

The application can still write its own service logs; those are different from a developer-authored Logger message. See Pipeline Logger if you need a formatted snapshot of pipeline sections.

Find the transaction

Search by custom fields

  1. In Monitor → Local Analytics, choose a date range containing the run. In Custom fields, enter OrderNo and 123, then select Search. Open the returned card to see the message and saved metadata.
  2. In OpenSearch → Analytics, select kestrel-execution-logs, enter the same field and value, and select Search. Expand the transaction, then its Logger step.
  3. For partial matching, enter *123*. Multiple field rows use AND semantics; OrderNo=123 and PoNo=567 must both match the same run.

Local Analytics reads run records from PostgreSQL. OpenSearch Analytics requires a configured OpenSearch connection and an indexed execution transaction. OpenSearch data can lag or expire independently of the local run record; its configuration has a separate retention policy.

Checks

If the message or search result looks wrong

SymptomCheck
Message stays at an older constant, such as System LogsOpen logMessage in Pipeline settings. Replace or delete its hardcoded value before mapping a source. Save mapping and workflow; inspect the Logger on the path that actually ran.
No Logger entry in a successful runCheck whether the Logger is on a normal path or an exception handler branch. Only executed steps write entries.
Custom-field search returns no runConfirm the run's date falls in the selected range; inspect the run's Custom fields display; check spelling and whether substitutions produced a nonempty value. Use * to match unknown prefixes or suffixes.
Run visible locally but absent in OpenSearchCheck OpenSearch configuration, the selected kestrel-execution-logs index, indexing health, and OpenSearch retention.
