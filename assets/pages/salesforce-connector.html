Workflow / Connectors / Salesforce

Call Salesforce from a workflow.

The Salesforce connector uses an enabled project Salesforce Connection to run a selected Salesforce API action. The workflow pipeline supplies request values and receives the HTTP response.

Design

Add a Salesforce step

  1. 1
    Prepare the connection

    Create and test an enabled Salesforce Connection in the same project.

  2. 2
    Place the connector

    Drag Salesforce from the workflow Connector tab onto the canvas and connect it in the execution path.

  3. 3
    Configure the action

    Double-click the step. Select Connection, API type, and Action. Supply an object API name, platform event API name, or Apex REST path when that action asks for one. Comment is optional.

  4. 4
    Map Step In and Step Out

    Open the settings icon. Map values to Salesforce_Request; map Salesforce_Response from Step Out to Pipeline Out when later steps need it. Changing API type or action resets the step's input contract, so review mappings after a change.

  5. 5
    Save and test

    Resolve workflow warnings, save, then run with test data. Use an Exception Handler for Salesforce or configuration failures.

Pipeline contract

Map request and response documents

All request fields live under ${pipeline.input.Salesforce_Request}. The editor generates only the fields needed for the chosen action. Use a source mapping or a deliberate constant. JSON object or list values supplied as body are serialized to JSON by the runtime; for Bulk CSV or Bulk XML, provide correctly formatted text for the selected action.

Step Out pathTypeMeaning
${pipeline.output.Salesforce_Response.recordId}StringREST record actions only. CREATE returns the generated ID; GET, UPDATE, and DELETE return the input record ID after success. It is absent if Salesforce did not return a create ID.
${pipeline.output.Salesforce_Response.statusCode}NumberSalesforce HTTP status, such as 201 for a created record.
${pipeline.output.Salesforce_Response.contentType}StringResponse Content-Type header, when supplied.
${pipeline.output.Salesforce_Response.headers}DocumentSalesforce response headers.
${pipeline.output.Salesforce_Response.body}Object or StringParsed JSON for JSON responses; raw text for CSV, XML, or other responses.

Step Out only becomes available to downstream pipeline paths according to mappings you save in the step settings. Do not map Pipeline In directly to Pipeline Out as a substitute for the connector result.

Worked examples

Start with a small REST operation

Create an Account: API type REST, Action Create record, Object API name Account. Set Salesforce_Request.body to a JSON document such as:

{
  "Name": "Acme Example Ltd",
  "Phone": "+1-415-555-0100"
}

Salesforce generates the ID. After a successful response, map Salesforce_Response.recordId to a downstream variable; do not include Id in the create body. The raw create response remains in Salesforce_Response.body.

Query Accounts: API type REST, Action Query SOQL; map Salesforce_Request.query to SELECT Id, Name FROM Account LIMIT 10. Query does not require an Object API name field.

Publish a platform event: API type EVENT_PROCESSING, Action Publish platform event, API name Demo_Notification__e, and Salesforce_Request.body containing fields defined on that event, for example {"Message__c":"Order ready"}. This publishes a platform event, not a legacy Generic Event. To consume the event, configure a separate Salesforce Trigger for the same event API name.

Apex Call and Event Processing

Call custom endpoints or publish platform events

For Apex Call, select a tested Salesforce connection, choose GET, POST, PUT, PATCH, or DELETE, and optionally enter a default relative Apex REST path such as orders. Kestrel prefixes /services/apexrest/. A leading slash or an existing /services/apexrest/ prefix is accepted and normalized. Map Salesforce_Request.path when the resource path varies by execution. Event Processing instead uses the configured platform event API name ending in __e and a mapped body; see the Salesforce Trigger for receiving events.

Apex Call pipeline

Use one path string and explicit key/value lists

The Step In document is Salesforce_Request. The path field is one String, even when the URL has several dynamic segments. Map a complete relative path from a previous step, or set a constant containing pipeline references. Kestrel substitutes those references during pipeline mapping before the Apex request runs. A nonempty mapped path takes precedence over the configured default path, so an unused default does not block the call. Pipeline references in the configured default path are also resolved at runtime.

Default path in step: orders
Salesforce_Request.path: accounts/${pipeline.input.webHookRequest.body.accountId}/orders/${pipeline.input.webHookRequest.body.orderId}
Resolved example: accounts/001ABC/orders/SO-1001
Sent path: /services/apexrest/accounts/001ABC/orders/SO-1001

Use a single mapped path for every method. Do not include a domain, query string, fragment, percent escape, or ... A leading slash or /services/apexrest/ prefix is accepted and normalized. A substituted value containing a slash becomes another path segment; validate or normalize external IDs before building the path. The older pathParams/pathParamList placeholder form remains readable for saved workflows, but new steps use the one path string.

Step In fieldTypeExampleBehavior
pathStringaccounts/001ABC/orders/SO-1001Optional when a default path is configured; overrides it when nonempty.
queryParamListDocumentList of name, value strings[{"name":"include","value":"lines"},{"name":"status","value":"open"}]Optional. Appended as URL-encoded query parameters. The same name may appear more than once.
headerListDocumentList of headerName, headerValue strings[{"headerName":"X-Correlation-Id","headerValue":"run-1001"}]Optional custom headers. Authentication and transport headers are managed by Kestrel and cannot be overridden.
bodyString (or mapped JSON document){"status":"Ready"}Shown for POST, PUT, PATCH; optional for DELETE only when enabled. GET sends no body.

Set Content type in the step configuration when a body is sent, for example application/json or application/xml. For JSON, a mapped document is serialized. For XML or plain text, map a string. The response exposes Salesforce_Response.statusCode (Number), contentType (String), headers (Document), and body (parsed JSON or text).

If Salesforce returns a non-2xx status, the step fails and the workflow error handler receives the issue. Query and header list values are optional; the selected connection supplies OAuth authentication. Review pipeline substitution for expression syntax and mapping behavior.

Bulk request and response formats

Set the format for each Bulk API action

For REST Bulk (Bulk API 1.0), double-click the Salesforce step and choose its API type and action. Request content type controls the HTTP Content-Type header and must match the actual Salesforce_Request.body. Response format controls the HTTP Accept header. Configure these separately on each Salesforce step; a Create job step does not transfer its selection to an Add batch step. The contentType field inside the job definition describes the format of later record batches. It is distinct from the HTTP request header used to create the job.

REST Bulk actionRequest content typeResponse formatPipeline input
Create jobJSON (application/json) or XML (application/xml). Automatic detects JSON when the body begins with {; otherwise XML.Automatic uses JSON for a JSON request, XML otherwise. JSON or XML may be selected explicitly.Salesforce_Request.body: job definition.
Add batchCSV (text/csv, default), JSON, or XML. Choose the format declared in the job definition.Choose JSON or XML according to the job; automatic defaults to XML.Salesforce_Request.jobId and body: records.
Close job / Abort jobXML (default) or JSON. Kestrel generates the Closed or Aborted state body in that format.Automatic defaults to XML unless JSON request content type is selected.Salesforce_Request.jobId; no mapped body.

JSON job example: Choose REST Bulk → Create job → Request content type JSON. Map a JSON document or JSON string to Salesforce_Request.body:

{
  "operation": "insert",
  "object": "Account",
  "contentType": "JSON"
}

This sends the job definition with HTTP Content-Type: application/json. For the next REST Bulk → Add batch step, set Request content type to JSON, map the returned job ID to Salesforce_Request.jobId, and supply the records in Salesforce's Bulk API JSON batch format. To upload CSV instead, create the job with "contentType":"CSV", select CSV on Add batch, and map CSV text such as Name,Phone Acme,+14155550100. Finish with Close job and poll Get job/Get batch for completion; creating a job alone does not upload records.

XML job example: Choose Request content type XML and map the following string to body. Its contentType declares CSV batches, so choose CSV on the later Add batch step.

<jobInfo xmlns="http://www.force.com/2009/06/asyncapi/dataload">
  <operation>insert</operation>
  <object>Account</object>
  <contentType>CSV</contentType>
</jobInfo>

For REST Bulk 2.0, the step shows the API's fixed formats instead of a selectable request content type: Create ingest/query job and state changes send JSON; Upload CSV sends text/csv; GET actions send no request body. An ingest Create Job body must be a JSON object with "contentType":"CSV" (or omit that field). Kestrel rejects "contentType":"JSON" for Bulk 2.0 ingest before sending the call. Example: {"object":"Account","operation":"insert","contentType":"CSV"}. Map the returned Salesforce_Response.body.id as jobId for Upload CSV and Close job. A JSON job definition does not mean JSON record upload.

For both API families, Salesforce_Response.statusCode is the Salesforce HTTP status. Salesforce_Response.contentType is the returned header; JSON responses become a document in Salesforce_Response.body, while XML and CSV remain strings. On failure the workflow Exception Handler receives the HTTP status and Salesforce's error message, including messages returned as Bulk API XML. The incoming webhook's HTTP 200 only confirms its own response; inspect the Salesforce step result to confirm job creation.

Failure handling

Route failures through the workflow

A missing or disabled connection, invalid object/path/ID, missing required request field, authentication failure, and non-2xx Salesforce response fail the step and are available to the workflow's Exception Handler. The message includes the API type, action, HTTP status, and a safe Salesforce error when available. A 401 response causes one token refresh and retry. Review the effect of retrying create, publish, or bulk operations because a remote request may have succeeded before Kestrel observed a response.

The connection's Test Connection verifies authentication and REST limits access only. An operation can still fail because the connected Salesforce user lacks object, field, event, Apex, or Bulk API permission.
