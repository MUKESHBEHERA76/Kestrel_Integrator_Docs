Administrator setup

Create a Webhook Auth alias

  1. 1
    Open Security → Webhook Auth

    Select Add Webhook Auth Alias. Alias management is available to Administrators.

  2. 2
    Name the alias

    Use a unique application-wide name containing letters, underscore, or hyphen, such as orders_webhook_auth.

  3. 3
    Select Auth type

    Choose Basic auth, API-Key, or JWT Token. Complete the type-specific fields below and select Create alias.

  4. 4
    Assign it to a workflow

    Open a Webhook Trigger, select the same authentication type, choose the matching alias, and save the workflow.

The alias belongs to the Kestrel application and can be reused by multiple project workflows. The alias type cannot be changed after creation; create a new alias if a different type is needed.

Basic auth

Validate a username and password

FieldRequirement
UserIDRequired username without spaces.
PasswordRequired. The current form policy requires 10–20 characters with uppercase, lowercase, and one of @, _, or -, without spaces.

The caller sends Authorization: Basic BASE64_USERID_COLON_PASSWORD. For example, HTTP clients can use their built-in Basic Auth option; they generate the header. The runtime checks both values against the selected alias and rejects a mismatch with HTTP 401.

API-Key

Validate a configured request header

FieldRequirement
Header nameRequired, without spaces; for example X-API-Key.
API keyEnter a secret without spaces or select Generate. If omitted when creating through the API, the backend generates one.

The caller sends the configured header, for example X-API-Key: YOUR_SECRET. Kestrel compares its value with the selected alias. The Webhook Trigger can specify the header name; ensure it matches the client request. Preserve a generated key securely at creation time because the alias view masks it.

JWT Token

Verify signed bearer tokens

Provide exactly one verification source:

FieldRequirement
JWKS URLAbsolute HTTPS URL of the issuer's JSON Web Key Set. Kestrel fetches and validates it when the alias is saved.
PEM Public KeyPublic verification key in PEM format, used instead of a JWKS URL.
Required ClaimsOptional claim names and JSON values; for example iss, aud, or role. Every configured claim must match.

The caller sends Authorization: Bearer TOKEN. Kestrel verifies a supported RSA or EC signature, token expiration and not-before time, and required claims. Supported algorithms are RS256, RS384, RS512, ES256, ES384, and ES512. Invalid tokens return HTTP 401.

For JWKS, configure the identity provider's public key endpoint, not a signing secret. Kestrel caches fetched keys briefly and refreshes them as needed.

Workflow configuration

Reference the alias from Webhook Trigger

  1. 1
    Open the trigger

    Double-click Webhook Trigger in the workflow editor.

  2. 2
    Select Authentication Type

    Choose Basic, API-Key, or JWT to match the alias type.

  3. 3
    Select the alias

    Choose the centrally managed alias from the matching dropdown. If none appears, ask an Administrator to create it in Security → Webhook Auth.

  4. 4
    Save and call the endpoint

    Send the matching Authorization or API-key header. See the Webhook Trigger guide for endpoint, body, pipeline, and response behavior.

i
Pipeline visibility

Credential-bearing headers such as Authorization and API keys are redacted in the workflow's copied request headers.

Operations

Rotate and retire aliases carefully

Use the row actions in Security → Webhook Auth to view or edit an alias. The view masks Basic and API-key secrets. For Basic or API-Key edits, leave a secret field empty to retain its encrypted value; enter a new value to rotate it. Update callers when you rotate credentials. JWT verification settings can be updated to follow key rotation.

Before deletion, Kestrel checks workflow references. Remove the alias from every referring Webhook Trigger before deleting it; deletion is rejected while it is in use. Authentication failures return HTTP 401 and do not start workflow execution.
