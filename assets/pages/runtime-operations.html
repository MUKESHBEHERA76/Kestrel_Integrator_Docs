Purpose and access

One view of the execution runtime

The page calls the runtime overview API when opened and refreshes every five seconds. Refresh is also available on demand.

RoleWhat it can do
Viewer or DeveloperRead the overview and investigate execution capacity and dependencies.
AdministratorRead the overview and request Pause, Drain, or Resume for a selected worker.

Worker controls are available through POST /api/execution/runtime/workers/{workerId}/pause, /drain, and /resume. They affect execution workers, not the entire application, other workers, trigger definitions, or existing workflow configuration.

Scope matters

Active executions and outbox counts come from the database. Worker presence comes from coordination heartbeats. Bulkhead and JDBC pool figures describe the runtime instance serving the overview request; do not add them up as a cluster-wide total.

Worker lifecycle

Pause, Drain, and Resume

Each button targets the worker shown on its card. A remote worker applies the request through coordination; the API responds that the request was accepted, and the next heartbeat shows the observed state.

ActionNew queued executionsAlready active executionsResulting state
PauseThe worker stops its RabbitMQ execution consumer and does not claim new commands.Pause does not request cancellation of active runs. The worker remains in the paused lifecycle state.PAUSED until resumed or the process lifecycle changes.
DrainThe worker stops taking new commands.Existing active work is allowed to complete. If none is active, drain completes immediately.DRAINING, then DRAINED when its active run count reaches zero.
ResumeThe worker restarts its consumer and can claim queued commands again, subject to capacity and dependency readiness.Existing work continues.RUNNING.
!
Pause and Drain are worker controls

Neither action disables a workflow trigger, deletes queue messages, cancels an already-running workflow, or stops another worker. When other workers are available, they can continue consuming the shared queue. If all workers stop consuming, new accepted commands can accumulate in RabbitMQ.

A button click returns 202 Accepted for the control request. It does not by itself prove that a remote worker has changed state. Watch its lifecycle badge, active run count, heartbeat age, and the queue consumer count. The control request is held in coordination for a configured time; it is not a permanent deployment setting.

Operating procedures

Use the controls in a predictable sequence

Planned worker restart

  1. Check that another worker is present if processing must continue.
  2. Select Drain for the worker being restarted.
  3. Wait for DRAINED and 0 active executions.
  4. Restart or replace the worker; verify a fresh heartbeat and RUNNING.

Temporarily stop new claims

  1. Select Pause on the affected worker.
  2. Confirm PAUSED and inspect queue backlog and other workers.
  3. Resolve the dependency or capacity issue.
  4. Select Resume and confirm consumers and active work recover.

Investigate slow processing

  1. Compare queue message count with oldest age and consumer count.
  2. Check execution-outbox pending age and RabbitMQ availability.
  3. Inspect worker heartbeats, active executions, bulkhead rejections, and JDBC waiters.
  4. Open execution analytics and logs for a specific run ID.
