Workflow / HTTP Request

Call REST, GraphQL, and SOAP APIs from a workflow.

HTTP Request is a workflow-only connector. Its configurator selects the API type; its pipeline supplies the URL, headers, authentication, request data, timeout, retry policy, and protocol-specific values at runtime.

Getting started

Add and configure the connector

HTTP Request is available in the Workflow Editor and is intentionally not available in the Reusable Service Editor.

  1. 1
    Open a workflow

    Drag HTTP Request from the HTTP Request connector category onto the workflow canvas.

  2. 2
    Open the configurator

    Double-click the step. Connector name is read-only; Comment is editable.

  3. 3
    Select API Type

    Choose REST, GraphQL, or SOAP. The workflow cannot be saved while the API type is missing.

  4. 4
    Open pipeline settings

    Select the step and use its settings icon. The Step In fields change to match the selected API type.

  5. 5
    Map deliberately

    Connect pipeline values or hardcode only the intended fields. HTTP Request does not automatically copy incoming fields into headers or other inputs.

  6. 6
    Map the response

    Map statusCode, responseHeaders, responseBody, and retryAttempts to the pipeline output fields needed by later steps.

!
Changing API Type changes the Step In contract

Review mappings after switching between REST, GraphQL, and SOAP because protocol-specific inputs are rebuilt for the selected type.

Common pipeline contract

Inputs available for every API type

Every field supports mapping from the workflow pipeline. Strings inside mapped documents and lists also support pipeline substitution.

i
Map, hardcode, or substitute

An exact expression such as ${pipeline.input.endpoint} keeps the original value type. Embedded expressions such as https://api.example.com/users/${pipeline.input.userId} are substituted into the surrounding string. The same recursive substitution applies inside headers, query parameters, authentication, GraphQL variables, form fields, and attachment documents.

Retry configuration

Retry only the HTTP statuses you choose

retryConfig is a Step In Document available for REST, GraphQL, and SOAP. Every child is a String pipeline variable.

Pipeline variableRequiredDefault / valid valuesMeaning
${pipeline.input.retryConfig.retry}Always available"false" by default; "true" or "false"Enables or disables status-code retries. Values are case-insensitive at runtime.
${pipeline.input.retryConfig.retrycount}When retry is "true"Positive whole-number String such as "1", "3", or "5"Maximum number of additional HTTP attempts after the initial request. Zero is not valid when retry is enabled.
${pipeline.input.retryConfig.retryIntervalInSec}When retry is "true"Positive whole-number String such as "1", "5", or "30"Seconds to wait before each additional attempt. Zero is not valid when retry is enabled.
${pipeline.input.retryConfig.retryStatusCodes}When retry is "true"Comma-separated HTTP codes from 100 through 599, for example "408,429,500,502,503,504"A retry occurs only when the response status is in this set and retrycount has not been exhausted.
 
retryConfig:
  retry: "true"
  retrycount: "3"
  retryIntervalInSec: "5"
  retryStatusCodes: "408,429,500,502,503,504"
  1. 1
    Initial request

    The first outbound request is not counted as a retry. retryAttempts starts at 0.

  2. 2
    Status evaluation

    If the response status is absent from retryStatusCodes, the connector returns it immediately, including 4xx and 5xx responses.

  3. 3
    Wait and retry

    For a configured status, the connector waits retryIntervalInSec and sends the same request again. retryAttempts increments only when the additional request is attempted.

  4. 4
    Final response

    The first non-retryable response, or the last response after retrycount is exhausted, becomes the normal Step Out response.

!
Conditional workflow validation

When retry is hardcoded to "true", workflow Issues requires all three companion fields and validates positive counts, positive intervals, and status-code syntax. Dynamically mapped values receive the same checks at runtime. The total timeoutMillis must be long enough for the request attempts and retry waits.

i
What is not retried

retryStatusCodes controls HTTP response retries. Configuration errors, invalid mappings, DNS/TLS/I/O failures, interruption, and an exhausted timeout raise their normal connector error instead of being selected by an HTTP status code.

Authentication document

Build authorization at runtime

Map credentials from secure pipeline values. Do not log authentication fields or hardcode production secrets in the workflow definition.

authTypeFields usedWhat the connector sends
NONENoneNo generated Authorization header. This is also the default when authType is empty.
BASICusername, passwordAuthorization: Basic <base64(username:password)>
BEARERbearerTokenAuthorization: Bearer <token>
OAUTH2_CLIENT_CREDENTIALStokenUrl, clientId, clientSecret; optional scope, audienceCalls the token endpoint using a form-encoded client-credentials request, then sends the returned token type and access token in Authorization.
!
API keys are explicit values

Place an API key directly in headers using the provider's required header name, or in queryParams when the provider explicitly requires a query key. No API key is added automatically.

API Type: REST

Send standard HTTP requests and raw bodies

REST adds method, requestBody, formFields, and attachments to the common inputs.

FieldTypeRequiredDescription and probable values
${pipeline.input.method}StringNoGET, POST, PUT, PATCH, DELETE, HEAD, or OPTIONS. Default: GET.
${pipeline.input.requestBody}StringAPI-dependentRaw UTF-8 JSON, XML, text, or another payload format understood by the API.
${pipeline.input.formFields}DocumentNoText parts used only when the explicitly mapped Content-Type starts with multipart/form-data.
${pipeline.input.attachments}Document ListNoBinary multipart parts supplied as Base64 or bytes from the pipeline.
 
url: https://api.example.com/orders
method: POST
headers:
  Content-Type: application/json
  Accept: application/json
requestBody: |
  {"customerId":"${pipeline.input.customerId}","amount":125.50}
timeoutMillis: 15000

The connector does not infer a body format. Set the matching Content-Type explicitly in headers.

API Type: GraphQL

Use one field for queries and mutations

GraphQL always uses POST. The connector builds a JSON envelope containing query and variables and defaults Content-Type to application/json.

FieldTypeRequiredDescription
${pipeline.input.graphqlQuery}StringYesGraphQL query or mutation text. Mutations are entered here, not in requestBody.
${pipeline.input.graphqlVariables}DocumentNoVariables object. It may be mapped as a document or entered as valid JSON text.
 
graphqlQuery:
  mutation CreateUser($name: String!, $email: String!) {
    createUser(name: $name, email: $email) {
      id
      name
      email
    }
  }

graphqlVariables:
  {
    "name": "${pipeline.input.name}",
    "email": "${pipeline.input.email}"
  }

The transmitted body is equivalent to {"query":"mutation ...","variables":{"name":"...","email":"..."}}.

API Type: SOAP

Send a complete SOAP XML envelope

SOAP always uses POST. Supply the final XML envelope in requestBody; the connector does not import a WSDL or generate an operation payload.

FieldTypeRequiredDescription and probable values
${pipeline.input.soapVersion}StringNo1.1 by default, or 1.2.
${pipeline.input.soapAction}StringService-dependentFor SOAP 1.1 it becomes the SOAPAction header. For SOAP 1.2 it is added as the Content-Type action parameter.
${pipeline.input.requestBody}StringYesComplete SOAP XML envelope. Pipeline expressions can be embedded in the XML.
 
url: https://www.dataaccess.com/webservicesserver/NumberConversion.wso
soapVersion: 1.1
soapAction: https://www.dataaccess.com/webservicesserver/NumberToWords
requestBody: |
  <?xml version="1.0" encoding="utf-8"?>
  <soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
    <soap:Body>
      <NumberToWords xmlns="http://www.dataaccess.com/webservicesserver/">
        <ubiNum>${pipeline.input.number}</ubiNum>
      </NumberToWords>
    </soap:Body>
  </soap:Envelope>

REST multipart requests

Send text fields and pipeline-supplied attachments

Multipart is a REST body format, not an API type. Activate it by explicitly mapping Content-Type: multipart/form-data in headers.

Attachment fieldRequiredDescription
${pipeline.input.attachments.fieldName}NoMultipart form field name. Defaults to file.
${pipeline.input.attachments.fileName}YesFilename included in Content-Disposition.
${pipeline.input.attachments.contentType}NoFile media type. Defaults to application/octet-stream.
${pipeline.input.attachments.contentBase64}One content fieldBase64-encoded content from the pipeline.
${pipeline.input.attachments.contentBytes}One content fieldByte array or numeric byte list from the pipeline. Takes precedence over contentBase64.
 
method: POST
headers:
  Content-Type: multipart/form-data
formFields:
  description: Monthly report
attachments:
  - fieldName: file
    fileName: report.pdf
    contentType: application/pdf
    contentBase64: ${pipeline.input.reportBase64}

Kestrel generates the multipart boundary and replaces the Content-Type value with multipart/form-data; boundary=....

Step Out contract

Receive the response without forced parsing

The connector returns transport-level results for every API type. Parse or map the response explicitly in later workflow steps.

Step Out fieldTypeDescription
${pipeline.output.statusCode}IntegerHTTP response status such as 200, 404, or 500.
${pipeline.output.responseHeaders}DocumentResponse header map. A header with one value is a string; repeated values are returned as a list.
${pipeline.output.responseBody}StringRaw response decoded using the response charset; UTF-8 is used when none is declared or the charset is invalid.
${pipeline.output.retryAttempts}IntegerNumber of additional HTTP attempts made. It is always 0 when no retry occurred, even when retry is disabled.
i
HTTP error statuses are still responses

A 4xx or 5xx response is returned through statusCode, responseHeaders, responseBody, and retryAttempts after any configured status-code retries finish. Use workflow logic to decide which final statuses are acceptable. Transport, timeout, and configuration failures raise connector errors.

End-to-end workflow example

Create an order with bearer authentication and controlled retries

This example maps an incoming customer identifier and access token, sends a REST request, retries temporary remote failures, and exposes the result to later workflow steps.

  1. 1
    Select REST

    Double-click HTTP Request and set API Type to REST.

  2. 2
    Open Step In

    Open pipeline settings. Hardcode stable request settings and map runtime values from the workflow pipeline.

  3. 3
    Configure retry

    Expand retryConfig and hardcode all four String children as shown below.

  4. 4
    Map Step Out

    Map response fields into named pipeline output variables for the IF step, logger, response step, or following connector.

  5. 5
    Review Issues

    Resolve any missing retry fields, invalid positive numbers, malformed status codes, or missing API Type before saving.

Step In
url = "https://api.example.com/v1/orders"
method = "POST"
headers = {
  "Content-Type": "application/json",
  "Accept": "application/json",
  "X-Correlation-Id": "${pipeline.input.correlationId}"
}
queryParams = {
  "source": "kestrel"
}
timeoutMillis = "30000"
authentication = {
  "authType": "BEARER",
  "bearerToken": "${pipeline.input.accessToken}"
}
requestBody = "{\"customerId\":\"${pipeline.input.customerId}\",\"amount\":125.50}"
retryConfig = {
  "retry": "true",
  "retrycount": "3",
  "retryIntervalInSec": "5",
  "retryStatusCodes": "408,429,500,502,503,504"
}

Step Out
${pipeline.output.statusCode}      -> ${pipeline.output.orderApiStatus}
${pipeline.output.responseHeaders} -> ${pipeline.output.orderApiHeaders}
${pipeline.output.responseBody}    -> ${pipeline.output.orderApiBody}
${pipeline.output.retryAttempts}   -> ${pipeline.output.orderApiRetries}
i
Example result

If the API returns 503, then 503, then 201, the connector sends three total requests and returns statusCode = 201 with retryAttempts = 2. If the first request returns 201, retryAttempts is 0.

Runtime and operational behavior

Timeouts, redirects, headers, and failures

These details are important when troubleshooting production integrations.

Timeout deadline

timeoutMillis must be positive. The remaining time is recalculated across OAuth2 token acquisition, every connection and response wait, and every configured retry interval.

Retry output

${pipeline.output.retryAttempts} is initialized to 0 before request execution and records only additional attempts, not the initial request.

Redirects

The Java HTTP client follows normal redirects. The final response is returned to the pipeline.

Explicit headers only

Inbound webhook and previous-step headers do not flow into the outbound request unless the developer maps them intentionally.

Restricted headers

Transport-controlled headers are ignored, including Host, Content-Length, Connection, Expect, Transfer-Encoding, Upgrade, HTTP/2 pseudo-headers, and related hop-by-hop headers.

Interrupted execution

An interrupted request restores the Java thread interruption flag and raises HTTP_REQUEST_INTERRUPTED.

Raw output

JSON, XML, GraphQL, SOAP, text, and error bodies remain strings so the workflow can choose its own parsing and data structure mapping.

Error codeMeaningTypical cause
HTTP_REQUEST_CONFIGURATION_ERRORThe request cannot be constructed.Missing URL/query/XML, invalid timeout, incomplete or invalid retryConfig, invalid Base64, unsupported method/auth type, or malformed GraphQL variables.
HTTP_REQUEST_TIMEOUTThe configured deadline expired.Slow token endpoint, connection, or remote API.
HTTP_REQUEST_INTERRUPTEDThe execution thread was interrupted.Runtime shutdown or cancellation.
HTTP_REQUEST_ERRORThe HTTP operation failed.Invalid URI, network/DNS/TLS problem, or I/O failure.
HTTP_OAUTH_ERROROAuth2 token retrieval failed.Non-2xx token response, invalid token JSON, or missing access_token.
!
Protect credentials and sensitive responses

Map secrets only into the field that needs them. Avoid Logger and Pipeline Logger for Authorization values, tokens, passwords, client secrets, attachment content, and sensitive response bodies.
